النطاق والضوابط

كل التفاعلات كانت من واجهة المتصفح. لم تُفتح اتصالات قاعدة بيانات، ولم يُنفّذ SQL أو اختبار CLI/API مباشر، ولم يُعدّل الكود أو الأدوار أو عضويات الفرق. اسم القاعدة مستند إلى تأكيد المستخدم لخدمة Railway. قاعدة cmms الأصلية خارج النطاق تمامًا.

الاختبارات السابقة قبل النشر ملغاة ولا تُستخدم كدليل في هذه الجولة. فُحصت PMV2، واستُبعدت الصيانة الدورية القديمة وتقريرها بحسب طلب المستخدم. السجلات القديمة وتكاليفها بقيت مؤجلة.

أهم النتائج الناجحة

  • الصرف التشغيلي: إنشاء بصنفين، وصول للمستودع، اعتماد واختيار لوت، صرف فعلي24 ريالًا، مرتجع جزئي ثم كامل. تطابق تقرير تكلفة اللوت، واستُعيدت كميات الاختبار.
  • مديرIT أنشأ أمر صرف جديدًا؛ المستودع كشف رصيده الصفري واقترح مسودة شراء. إنشاء المسودة نفسه فشل ضمن عطل المشتريات.
  • PMV2: إنشاء برنامج وهدف ومهمة محددة، بدء التنفيذ بالأدمن، نتيجة سليم، وإنهاء الزيارة. الزمن بدأ من الصفر. عُطّل برنامج الاختبار60001 لمنع تكرار المهام.
  • الفنيون دخلوا مهامي اليوم بالتبويبين وبطاقات الحالات؛ قوائم الدهان والتكييف والبلاغات المسندة بالاسم اختلفت حسب الحساب. مُنع ROBIL وSUHAIL من /users، وأُعيد sahid من /purchase-orders إلى مهامه.
  • المستودع عرض فنيًا فقط عند إنشاء المستخدم، ولم يظهر إنشاء تسوية في واجهته. المحاسب والإدارة العليا مُنعا من صفحة المستخدمين المباشرة.
  • لوحة الأدمن: نافذة تفاصيل بطاقة البلاغات فتحت66 سجلًا موافقًا لعدادها، مع الأعمدة والروابط والإغلاق. تنزيل سند الصرف نجح، ومحتوى PDF لم يُفحص.

مركز التحسين والتطوير: اقتراح بسيط يؤدي الغرض

  1. إصلاح تحميل الأفكار وحفظها أولًا، وإظهار فشل التحميل بوضوح.
  2. إبقاء نموذج الإنشاء قصيرًا: عنوان، مشكلة، هدف، فائدة، موقع وقسم، والأصل/المرفقات اختياريان. نقل المقاييس الإضافية إلى قسم قابل للفتح.
  3. بعد نجاح الأساس، اختبار المراحل الحالية بتسلسل واضح: تصنيف، دراسة تكلفة، موافقة، مستند تنفيذ مرتبط، نتائج، إغلاق. لا حاجة لإضافة شاشات أو مسارات مكررة.
  4. عرض مرجع التنفيذ وصافي تكلفته دون إعادة إدخال أو ازدواج شراء/صرف. هذه توصية للاختبار بعد إصلاح العطل، وليست ميزة تحققت في هذه الجولة.
