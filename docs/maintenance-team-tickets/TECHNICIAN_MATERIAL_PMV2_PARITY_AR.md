# تجربة «تحتاج مواد» للفني في تذاكر الصيانة

تاريخ التنفيذ: 2026-10-11، بعد موافقة المستخدم «نفذ الآن». لا اتصال بقاعدة البيانات ولا تشغيل للتطبيق أثناء التنفيذ أو الاختبار.

## المقارنة

| الجزء | قبل | بعد |
| --- | --- | --- |
| اختيار تحتاج مواد | تجهيز قائمة ثم فحص يدوي وتأكيدات متعددة | تثبيت حالة انتظار المواد، ثم تسجيل كل مادة بإجراء مستقل |
| اختيار الصنف | بحث عام دون ترتيب حسب الرصيد أو الاستخدام | مواد متوفرة بمخزن الفريق أولًا، ثم مواد سبق طلبها للفريق أو الهدف |
| الرصيد | زر فحص منفصل | فحص تلقائي للكمية والصنف المختارين، مع إعادة التحقق عند الحفظ |
| الرصيد الكامل | تأكيدات داخل قائمة المواد | نافذة تأكيد استلام تعرض الصنف والكمية والوحدة والمخزن؛ لا صرف دون التأكيد |
| الرصيد الجزئي | الطلب الجماعي الحالي | تسجيل كامل الاحتياج وإرسال النقص للتوفير، دون صرف الجزء المتوفر تلقائيًا |
| صنف غير مدرج | وصف يحتاج مطابقة | حفظ وصف الفني ووحدته وكمّيته؛ المستودع يطابق الصنف ثم يعاد حساب النقص |
| مادة إضافية | لا إضافة أثناء انتظار الطلب الأول | إضافة مادة أخرى أثناء الانتظار دون تكرار طلب أو صرف المادة السابقة |
| الاستلام بعد التحويل/الشراء | يمنع الاستلام الذاتي للفني عند وجود ربط توفير | بعد وصول التحويل الخاص بالاحتياج إلى مخزن الفريق يمكن للفني تأكيد الاستلام؛ صرف المستودع لمستلم فعلي يظل مدعومًا دون صرف مكرر |
| فصل الاحتياجات | ربط مستقل بالتذكرة | يبقى الربط بالتذكرة وبندها والإسناد والاحتياج؛ وصول تحويل لاحتياج آخر لا يكمل هذا الاحتياج |

## دورة العمل

1. الفني يختار «تحتاج مواد»، ويبحث بالاسم أو الكود، ويحدد الكمية. وحدة الصنف تأتي من الكتالوج.
2. إذا كان الرصيد كاملًا تظهر نافذة تأكيد الاستلام. التأكيد فقط يستدعي سند الصرف الأصلي باسم المستلم الحقيقي. انخفاض الرصيد بعد المعاينة يحفظ الاحتياج منتظرًا بدل تسجيل استلام وهمي.
3. عند النقص، يظهر الطلب في تبويب «تذاكر الصيانة» داخل `/scheduled-maintenance/warehouse-requests`. المستودع يطابق الوصف غير المدرج عند الحاجة، ثم يتابع التحويل أو الشراء بالنماذج والكتاب الحاليين.
4. رصيد الرئيسي يغطي النقص: تحويل إلى مخزن الفريق. عند عدم كفايته: شراء العجز غير المغطى بالرصيد أو الطلبات المعلقة، ثم الاستلام الفعلي في الرئيسي والتحويل إلى الفريق. اعتماد طلب الشراء وحده لا يثبت الاستلام.
5. بعد وصول التوفير الخاص بالاحتياج، تأكيد الفني أو صرف المستودع لمستلم فعلي ينشئ الصرف مرة واحدة. لا تصبح المهمة جاهزة للإصلاح قبل استلام جميع احتياجات الجولة.
6. تفاصيل الإصلاح تبقى إلزامية، والاستخدام والمرتجع يبقيان مربوطين بسند الصرف واللوت الأصليين. الاعتماد والإغلاق الفعليان عبر مسار التذكرة الحالي.

## الملفات وحدود المخاطرة

| الملف التشغيلي | الغرض | المخاطرة |
| --- | --- | --- |
| `client/src/pages/maintenance-teams/TicketMaterialNeedPanel.tsx` (جديد) | اختيار مادة وفحص تلقائي وتأكيد استلام | منخفضة إلى متوسطة: نموذج جديد بواجهات البرنامج الحالية |
| `client/src/pages/maintenance-teams/ExecutionPanel.tsx` | إدراج النموذج واستلام المادة وعرض السجل المقروء | متوسطة: واجهة التنفيذ القائمة |
| `server/routers/maintenance-teams/execution.router.ts` | إجراءات مصادق عليها وبحث حسب الرصيد والسجل | متوسطة: القراءة والمسار الجديد يحتاجان اختبارًا عمليًا على محرك القاعدة |
| `server/maintenance-team-tickets/service.ts` | تسجيل مستقل ومنع التكرار وإعادة فحص الصرف والتوفير | متوسطة: معاملات مواد التذاكر مع إعادة استخدام كتاب المخزون الأصليين |
| `shared/maintenance-team-tickets/material-routing.ts` (جديد) | حفظ النقص الأولي في سجل الإجراء القائم وحساب التوفير الخاص بالاحتياج | متوسطة: تمييز الاحتياج دون تعديل المخطط |
| `shared/maintenance-team-tickets/warehouse-materials.ts` | عدم تصنيف مادة جاهزة قبل وصول توفيرها الخاص | منخفضة إلى متوسطة |
| `server/routers/maintenance-teams/execution.workflow.ts` | عرض رسالة الإجراء المقروءة في إشعار المستودع والفني | منخفضة: نفس المستلمين وروابط الإشعار |

لا تغييرات في مخطط القاعدة ولا أوامر SQL مطلوبة. النقص الأولي محفوظ ببيانات مُصدّرة بإصدار في حقل ملاحظة إجراء الاحتياج القائم، ويعرض كنص مقروء في سجل الفريق والإشعارات. الاحتياجات القديمة ذات الملاحظات النصية تحتفظ بسلوكها ولا يعاد ترحيلها. لا إنشاء مهام PMV2 وهمية أو مستودعات أو فنيين جدد. واجهات PMV2 وخدماته الأصلية، والإسناد بالاسم، وصلاحيات B، والعائق والخارجي والإغلاق لم تعدل.

هذا تطبيق لتجربة المواد على ربط التذاكر المستقل، وليس استدعاء خدمة PMV2 المرتبطة بمهمة وزيارة. حد 20 مادة في الجولة وعقد الكميات الصحيحة الحالي للتذاكر محفوظان. الكميات الكسرية التي قد يدعمها PMV2 بحسب الوحدة لم تضف إلى التذاكر؛ تحتاج تغييرًا منفصلًا في عقد البيانات والكتاب والمخطط إذا طلبها المستخدم.

## التحقق

- 189 اختبار Node معزولًا، و26 اختبارًا لواجهات التنفيذ والمستودع، و15 اختبارًا جديدًا لنموذج المواد، و15 اختبارًا لتبويبي مهام اليوم: 245 اختبارًا ناجحًا. أعيدت اختبارات جسر التذكرة والإشعارات بعد تعديل عرض الرسالة، وتحقق عدم إرسال طلب مستودع قبل تسجيل مادة.
- حارس استيراد يمنع وحدات اتصال القاعدة وبيئتها في اختبارات Node. استدعاءات الواجهة محاكاة؛ اختبارات الواجهة تفحص المكونات والأحداث دون جلسة متصفح حيّة.
- مقارنة TypeScript بمصادر الملفات المحفوظة قبل التنفيذ: 663 تشخيصًا قبل وبعد، دون تشخيص جديد أو محذوف بعد تجاهل أرقام السطور. فحص المشروع العام لا يزال غير ناجح لأخطاء سابقة.
- نجح تحويل مصدر ملفات التشغيل السبعة؛ لا تحميل لوحدات التطبيق أو اتصالاتها في هذا الفحص.
- الاختبار المعزول لا يثبت نجاح SQL على TiDB أو الكتابة الفعلية واللوتات في بيئة المستخدم. لا ادعاء بانعدام المخاطرة أو اجتياز اختبار حي.

## اختبار المستخدم

1. افتح تذكرة مسندة إلى فريق من تبويب «تذاكر الصيانة» في مهامي اليوم، ثم اختر تحتاج مواد.
2. صنف متوفر: حدد الكمية، راجع المعاينة، وألغ نافذة الاستلام أولًا للتأكد أن الإلغاء لا يصرف. أكدها بعد ذلك وتحقق من المستلم الحقيقي وسند الصرف.
3. تذكرة أخرى بصنف ناقص: سجله وافتح تبويب المستودع؛ تحقق أن الكمية المطلوب توفيرها هي النقص. أضف مادة ثانية أثناء الانتظار وتحقق من استقلال ربطها وعدم تكرار الأولى.
4. اختبر التحويل من الرئيسي؛ ثم حالة الشراء والاستلام في الرئيسي والتحويل. قبل التحويل لا يتاح تأكيد الاستلام، وبعده أكد من حساب الفني. اختبر صرف المستودع أيضًا وتأكد أنه لا يسمح بتأكيد صرف ثانٍ.
5. سجل كمية الاستخدام وأكمل الإصلاح، ثم اختبر المرتجع إلى السند واللوت الأصليين ومراجعة المسؤول. اختبر تذكرة مسندة بالاسم للتأكد من بقاء مسارها المعتاد.

نُقلت ملفات التشغيل السبعة وحدها إلى نسخة `CMMSFINAL - Copy (2)` بعد التحقق من مصادرها الأصلية واعتمادياتها، واجتياز مراجعة صلاحية الكتابة خارج مساحة العمل، وتطابق SHA-256 لجميع الملفات مع النسخة المختبرة. لم ينقل أي إعداد اتصال أو يشغل التطبيق. التقارير وأدوات الاختبار في `CMMSFINAL`.
