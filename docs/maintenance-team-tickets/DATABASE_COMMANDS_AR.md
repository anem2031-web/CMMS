# أوامر قاعدة طبقة فرق تذاكر الصيانة

هذه أوامر معدة للمراجعة والتنفيذ اليدوي بواسطة صاحب المشروع فقط. لم ينفذها الوكيل ولم يتصل بالقاعدة. لا يبدأ الربط بتطبيقها وحدها.

## طريقة التنفيذ

1. اختر قاعدة المشروع المقصودة بنفسك. نفذ `00_preflight.sql` وحده. المتوقع صفر صفوف. إذا ظهر اسم جدول قائم، توقف وأرسل النتيجة؛ لا تستبدل الجدول ولا تستخدم IF NOT EXISTS لإخفاء الاختلاف.
2. نفذ أمر الإنشاء رقم 01 فقط، ثم أمر التحقق V01 فقط وأرسل نتيجته. استمر بنفس النمط بعد مراجعة النتيجة: 02 ثم V02، وهكذا حتى 09 ثم V09.
3. بعد التحقق من كل جدول، نفذ `10_verify_all_tables.sql` وحده. المتوقع تسعة صفوف.
4. كل ملف SQL يحتوي عبارة واحدة. لا تجمع الملفات في تنفيذ واحد. إذا فشل أمر، توقف عنده وأرسل نص الخطأ. أوامر التحقق للقراءة فقط.

## حدود هذه الدفعة

- إضافة تسعة جداول مستقلة فقط. لا ALTER/DROP/DELETE/UPDATE/INSERT/TRUNCATE على الجداول الحالية، ولا نسخ فرق PMV2 أو إنشاء مهام PMV2، ولا بيانات تجريبية في القاعدة.
- فصل جدول احتياج المواد عن سند الصرف: تعدد الدفعات يعني عدة روابط صرف للاحتياج الواحد. الطلب نفسه يسجل كإجراء `needs_material`، وصفوف الاحتياج تجمع بواسطة الإسناد ودورة المواد. لذلك لا يلزم جدول رأس طلب إضافي في هذه النسخة.
- `sourceId` في رابط الشراء يعني **معرف بند طلب الشراء**؛ في التحويل يعني معرف سجل التحويل الفعلي. لا تستخدم معرف رأس شراء مكان معرف البند.
- `stage='closed'` تعني اكتمال تنفيذ الفريق داخل الطبقة. إغلاق تذكرة الصيانة الفعلية يبقى في الورك فلو الحالي ويحتاج الربط المعتمد.
- الروابط الأجنبية الفيزيائية في هذه الدفعة بين الجداول الجديدة فقط. مراجع users/tickets/ticket_items/warehouses/catalog والوثائق القائمة تحتاج تحققًا بالخادم عند الربط. حماية حذف التذكرة/البند قبل فصل روابط الطبقة **شرط قبل التفعيل**؛ لا تستخدم غياب FK خارجي لتجاوزها.
- الكميات INT بما يتوافق مع سندات الصرف والمرتجع التي قدمها صاحب المشروع. لا توسيع كميات السندات الحالية أو تحويل وحدات تلقائي.
- `ticket_team_material_needs.usedQuantity=NULL` يعني لم يصرح الفني باستخدام الصنف؛ الصفر يعني لم يستخدم منه. المرتجع المعلق للصنف = مجموع المصروف - إجمالي الاستخدام - مجموع المرتجع الفعلي.
- `ticket_team_delivery_links.usedQuantity` لا يحدده الفني لكل سند: يظل NULL أثناء انتظار اختيار المستودع لدفعات المرتجع، ثم يصبح المصروف من السند ناقص المرتجع الفعلي منه عند اكتمال التوزيع. إذا استخدمت الكمية كاملة، يحسم السند مباشرة دون مرتجع.
- إعادة النتيجة للفريق تبدأ دورة مواد جديدة وتحافظ على سجلات الاستهلاك والمرتجع السابقة.
- مفتاح العملية حساس لحالة الأحرف. فهارس UNIQUE للعمليات والسندات مع قفل الإسناد والتحقق من revision مطلوبة عند إعداد موصل القاعدة. اختبارات الذاكرة لا تثبت أقفال TiDB.
- صحة DDL على القاعدة الفعلية لم تختبر؛ نتائج التنفيذ اليدوي وSHOW CREATE هي الدليل. لا توجد هنا أوامر تراجع تحذف البيانات أو تعيد بناء جداول قائمة.

## تحديث أمر 05 بعد مطابقة PMV2

أضيف عمود `usedQuantity INT NULL` في ملف الإنشاء 05 لحفظ الاستخدام الإجمالي للصنف. هذا تعديل على ملف SQL المعد فقط، وليس تغييرًا منفذًا على القاعدة. لا ينشئ مخزونًا ولا يرحل أي كمية.

إذا لم تنفذ الإنشاءات، استخدم الحزمة المحدّثة بدءًا بالفحص 00 وبنفس ترتيب الأمر الواحد ثم النتيجة. إذا سبق إنشاء جدول الاحتياج بالنسخة القديمة، لا تعِد CREATE؛ أرسل نتيجة أمر V05 للقراءة فقط أولًا، وبعد مراجعتها يُعد أمر التغيير المطلوب منفصلًا لتنفذه يدويًا. لا يوجد ALTER منفذ أو مقترح بلا معرفة البنية الفعلية.
