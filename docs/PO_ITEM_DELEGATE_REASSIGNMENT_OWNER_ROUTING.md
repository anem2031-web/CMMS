# إعادة تعيين المندوب على مستوى الصنف — التوجيه لنفس مراجع الطلب الأصلي

تاريخ التنفيذ: 2026-08-13

## 1. الطلب

آلية إعادة تعيين المندوب على مستوى الصنف داخل طلب الشراء:

> تعيين مندوب → لم يُسعّر الصنف → يظهر زر إعادة التعيين → المندوب يرسل الطلب والسبب →
> الصنف يتوقف مؤقتًا → **الطلب يعود لنفس الشخص الذي عيّن المندوب** → يختار مندوبًا جديدًا →
> المندوب الجديد يستكمل التسعير.

الشرط الجوهري: الطلب يعود **لنفس المستخدم** الذي اعتمد المراجعة واختار المندوب لهذا الصنف
تحديدًا — قد يكون المالك، الأدمن، مدير الصيانة، مدير الصيانة العامة، أو مدير الإنشاءات
والمشتريات، حسب من راجع ذلك الطلب فعليًا. ليس بثًّا لكل من يحمل أحد هذه الأدوار.

## 2. الحالة عند البدء

الميزة كانت مبنية مسبقًا بنسبة كبيرة (`INSTALL_DELEGATE_CHANGE_AR.txt`،
`drizzle/migrations/2026_08_01_add_po_item_delegate_change_request.sql`، عمود
`purchaseOrderItems.delegateChangeRequestedAt`/`delegateChangeRequestedById`/`delegateChangeReason`)،
وكل الشروط الجانبية (زر الطلب يظهر فقط قبل التسعير، السبب إلزامي، منع طلبَين متزامنَين،
تحديث ذري بلا سباق تزامن) كانت صحيحة ومطابقة للمواصفة.

**الفجوة الوحيدة:** الحسم والإشعار كانا يذهبان لأي مستخدم يحمل أحد الأدوار الخمسة
(`DELEGATE_CHANGE_RESOLVER_ROLES`) — بثًّا جماعيًا، لا لشخص محدد. هذا يخالف "الطلب يعود
لنفس الشخص الذي عيّن المندوب" حرفيًا: أي مدير من الثلاثة كان يستطيع حسم طلب لم يراجعه هو،
وقد يحوّل الصنف لمندوب لا يعرف السياق الذي اختير المندوب الأول لأجله أصلًا.

## 3. مصدر الحقيقة المستخدَم

`purchaseOrders.reviewedById` — يُسجَّل في **نفس الإجراء ونفس اللحظة** التي تُعيَّن فيها
`delegateId` لكل صنف (`approvals.router.ts::reviewItems`، ضمن معاملة واحدة). فهو يطابق
تمامًا "من اختار المندوب لهذا الصنف أصلًا" دون الحاجة لعمود جديد أو migration.

تحقّق أن هذا هو المصدر الوحيد فعليًا: `delegateId` يمكن تمريره اختياريًا عند إنشاء الطلب
(`create`)، لكن التعليق في الكود يوثّق أنه قيمة مبدئية تُستبدَل دومًا عبر `reviewItems`،
وحالة الصنف `pending` القابلة للتسعير لا تتحقق فعليًا (تُصبح قابلة للعمل من المندوب) إلا بعد
أن يتجاوز طلب الشراء `pending_review` عبر هذا الإجراء بالذات.

## 4. ما نُفِّذ

| الملف | التغيير |
|---|---|
| `server/_core/authz/engine.ts` | `DelegateChangeSubject.reviewedById` جديد؛ `canResolvePOItemDelegateChange` يشترط `ctx.userId === subject.reviewedById` |
| `server/routers/purchase/purchase-orders.router.ts` | `requestDelegateChange`: الإشعار يذهب لـ`po.reviewedById` تحديدًا بدل بث؛ `resolveDelegateChange`: يمرّر `reviewedById` للحارس |
| `server/routers/purchase/actionable.ts` | قائمة "بانتظار إجرائي" مقيّدة بنفس شرط الحارس، فلا يرى مدير غير مخوَّل طلبًا لا يقدر على حسمه |
| `client/src/pages/purchase/PurchaseOrderDetail.tsx` | `canManageDelegateChange` مقيّدة بنفس الشرط؛ الشارة ونص الحوار يعرضان اسم المراجع الفعلي بدل "مدير الصيانة" |
| `server/tests/authz.test.ts`, `server/tests/splitMaintenanceRoles.test.ts` | اختبارات جديدة تغطي التقييد والاستثناء والتوافق الرجعي |

### الحارس (`canResolvePOItemDelegateChange`)

```
baseEligible = دور من DELEGATE_CHANGE_RESOLVER_ROLES + الصنف pending + بلا batch + طلب معلّق فعليًا
إن لم يتحقق baseEligible → false
إن كان owner/admin → true دائمًا (صمام أمان — مثلًا مغادرة المراجع الأصلي الشركة)
إن كان po.reviewedById غير مسجَّل (null/undefined) → true (توافق رجعي لطلبات قديمة)
غير ذلك → subject.reviewedById === ctx.userId
```

### الإشعار عند الطلب

يذهب لـ`po.reviewedById` تحديدًا. عند غيابه (طلب قديم بلا مراجع مسجَّل) يُبث لكل مديري
المشتريات كما كان سابقًا — نفس امتداد التوافق الرجعي في الحارس تمامًا، فلا يُترك طلب بلا
أي مستلم.

### الواجهة

- زر «إعادة تعيين المندوب» (أُعيدت تسميته من "تغيير المندوب" لمطابقة مصطلح المستخدم) —
  لم يُعدَّل شرط ظهوره لأنه كان مطابقًا للمواصفة أصلًا: `role === "delegate" && item.delegateId === userId && !item.estimatedUnitCost`
  ضمن صنف `pending` بلا `batchId` ولا طلب معلّق سابق.
- شارة "بانتظار …" وحوار الطلب يعرضان `po.reviewedByName` (متوفر أصلًا من
  `getPurchaseOrderById` عبر LEFT JOIN)، فلا يبقى نص عام مضلِّل ("مدير الصيانة") حين يكون
  المراجع الفعلي شخصًا آخر.

## 5. قاعدة البيانات

**لا Migration ولا DDL.** كل الأعمدة المستخدَمة (`purchaseOrders.reviewedById`,
`purchaseOrderItems.delegateChangeRequestedAt` وما يرافقها) موجودة أصلًا من قبل هذا التعديل.

## 6. قيود معروفة / خارج النطاق

- **لا سلسلة تتبّع عبر إعادات تعيين متتالية.** لو أُعيد تعيين الصنف لمندوب ثانٍ ثم طلب هو
  الآخر تغييرًا، يعود الطلب مجددًا لـ`po.reviewedById` **الأصلي** — لا لمن حسم الطلب السابق.
  هذا مقصود ومطابق لصياغة المستخدم الحرفية ("في الأصل")، ويُبقي مصدر القرار واحدًا ثابتًا
  بدل سلسلة متغيرة يصعب تتبعها.
- **owner/admin يتجاوزان القيد دائمًا.** قرار مقصود كصمام أمان (مطابق لنمط `BYPASS_ALL_ROLES`
  المستخدَم في بقية النظام)، لا استثناء يحتاج تفعيلًا يدويًا.
- لم يُختبر البناء (`tsc`/`vitest`) في بيئة التنفيذ لعدم توفر `node_modules`؛ التحقق كان
  بالقراءة ومطابقة اختبارات `authz.test.ts` الموجودة يدويًا لمنطق الحارس الجديد.
