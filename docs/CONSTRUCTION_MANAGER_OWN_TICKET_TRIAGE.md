# تصنيف مدير الإنشاءات والمشتريات لبلاغه الشخصي فقط — بنفس آلية مدير الصيانة العامة

تاريخ التنفيذ: 2026-08-13

## 1. الطلب

مدير الإنشاءات والمشتريات يستطيع تصنيف بلاغه الشخصي فقط (الذي أنشأه هو)، باستخدام **نفس
آلية التصنيف وبقية سير العمل** المستخدَمة مع مدير الصيانة العامة حرفيًا — لا شاشة أو حقول
مختلفة. الفرق الوحيد المطلوب: نطاقه مقصور على بلاغه هو، لا كل الطابور.

قرار تصميم اتُّخذ بموافقة صريحة من صاحب المشروع (الخيار "أ" من خيارين مطروحين): التصنيف يتم
**من صفحة تفاصيل البلاغ مباشرة**، لا من فتح شاشة `/triage` المشتركة له (التي تعرض طابور كل
المستخدمين ولم تكن ستُفلتَر تلقائيًا).

## 2. اكتشاف وفّر معظم العمل: الحوار موجود مسبقًا وجاهز حرفيًا

عند الفحص، وُجد أن `TicketDetail.tsx` يحتوي **أصلًا** زرًا وحوار تصنيف كاملَين (`canTriage`,
`showTriageDialog`) يُستخدَمان اليوم من مدير الصيانة العامة — نفس الحوار الذي بحثناه سابقًا
بشاشة `/triage` (اختيار جهة/جهات، اختيار مسؤول كل جهة، عنوان تنظيمي للإنشاءات، ملاحظات).
الحوار **بلا أي قيد دور داخلي** — يستخدم `generalManagers`/`constructionManagers` المحسوبَين
من قائمة المستخدمين الكاملة بلا تمييز حسب من يفتح الحوار.

**النتيجة:** لم تكن هناك حاجة لبناء أي واجهة جديدة. القيد الوحيد الذي كان يمنع مدير الإنشاءات
من رؤية هذا الزر أصلًا هو شرط `canRouteTicket` (فحص دور فقط، لا يشمل دوره).

## 3. لماذا `triageMulti` تحديدًا (لا `triage`/`triageTicket`)

كل بلاغ جديد يُنشأ بـ`workflowModel: "department_tasks"` دائمًا (`tickets.router.ts::create`).
مسارا `triage` و`triageTicket` (الفرز أحادي الجهة، النموذج القديم) **يرفضان صراحة** أي بلاغ
بهذا النموذج:
```ts
if (ticket.workflowModel === "department_tasks") {
  throw new TRPCError({ ..., message: "هذا البلاغ يستخدم هيكل الجهات والمهام؛ استخدم فرز الجهات المعتمد" });
}
```
فأي بلاغ ينشئه مدير الإنشاءات اليوم **لا يمكن تصنيفه إلا عبر `triageMulti`**. الحوار الموجود
مسبقًا يفتح افتراضيًا بوضع `"multi"` عند الضغط على الزر — متوافق تمامًا مع هذا القيد بلا أي
تعديل.

## 4. ما نُفِّذ (3 ملفات)

| الملف | التغيير |
|---|---|
| `server/routers/_shared/procedures.ts` | إضافة `CONSTRUCTION_PROCUREMENT_MANAGER` لقائمة أدوار `ticketTriageProcedure` |
| `server/routers/tickets/tickets.workflow.ts` | دالة جديدة `assertConstructionManagerOwnTicketForTriage` تُستدعى داخل `triage`/`triageMulti`/`triageTicket` الثلاثة |
| `client/src/pages/tickets/TicketDetail.tsx` | توسيع `canRouteTicket` ليشمل دوره **مقيَّدًا بملكية البلاغ** (`ticket.reportedById === user.id`) |

### لماذا القيد مطبَّق مرتين (سيرفر + واجهة) لا مرة واحدة

`ticketTriageProcedure` فحص **دور** فقط — لا يستطيع التمييز بين بلاغ المستخدم وبلاغ غيره
بنيويًا. فمجرد إضافة دوره لقائمتها كان سيمنحه صلاحية تصنيف **أي** بلاغ في الطابور، لا بلاغه
فقط. لذلك أُضيف حارس ملكية صريح **داخل كل إجراء على حدة**، بعد جلب البلاغ مباشرة:

```ts
function assertConstructionManagerOwnTicketForTriage(actor, ticket) {
  if (actor.role !== CONSTRUCTION_PROCUREMENT_MANAGER) return;   // بقية الأدوار غير مقيَّدة
  if (ticket.reportedById !== actor.id) {
    throw new TRPCError({ code: "FORBIDDEN", message: "يمكنك تصنيف البلاغات التي أنشأتها بنفسك فقط" });
  }
}
```

هذا الحارس هو **مصدر الحقيقة الوحيد الملزِم أمنيًا** — يرفض أي محاولة تصنيف لبلاغ غيره حتى لو
استُدعي الإجراء مباشرة عبر API متجاوزًا الواجهة. تعديل `canRouteTicket` بالواجهة (نفس شرط
الملكية حرفيًا) هو طبقة تجربة مستخدم فقط (يُخفي الزر مسبقًا بدل إظهاره ثم رفضه من السيرفر) —
لا تعتمد عليه وحده لفرض القيد.

بقية الأدوار المسموح لها بـ`ticketTriageProcedure` (مدير الصيانة العامة، المالك، الأدمن) لا
تتأثر بهذا الحارس إطلاقًا — نطاقها الأوسع (تصنيف أي بلاغ في الطابور) بقي كما هو بلا تغيير.

### أثر جانبي فُحص ولا خطر منه

`ticketTriageProcedure` تحكم أيضًا إجراءً رابعًا: `assignForInspection`
(`tickets.approvals.ts`). هذا الإجراء **مُعطَّل عمدًا مسبقًا** — يرمي `BAD_REQUEST` دائمًا بغض
النظر عن من يستدعيه (بقايا توافق رجعي توجّه لاستخدام الفرز المعتمد بدلًا منه). إضافة دوره
لقائمة `ticketTriageProcedure` لا تُفعِّله له ولا لغيره — يبقى معطَّلًا للجميع كما كان.

## 5. قاعدة البيانات

**لا Migration ولا DDL.** تعديل منطق صلاحيات فقط.

## 6. قيود معروفة / خارج النطاق

- **بلاغات أخرى غير بلاغه تبقى غير قابلة للتصنيف من طرفه** — لا زر ولا إجراء سيرفر يقبله،
  حتى بعد توسيع رؤيته العامة للبلاغات (البند السابق بتاريخ 2026-08-13). التصنيف يبقى الاستثناء
  الوحيد المقصور على بلاغه، بينما الاستعراض مفتوح للجميع كما نُفِّذ سابقًا.
- شاشة `/triage` المشتركة **لم تُفتح له** ولم تُلمس إطلاقًا — قرار مقصود (الخيار "أ").
- `ticketProcedure` (`submitForTriage`/`delete`/`confirmCompletion`) لم يُمس — نقطة منفصلة
  نوقشت سابقًا ولم يُطلَب تنفيذها هنا.
- لم يُختبر البناء (`tsc`) في بيئة التنفيذ لعدم توفر `node_modules`؛ التحقق كان بالقراءة
  وتتبع كل استدعاء للدوال المعدَّلة، مع مطابقة توازن الأقواس آليًا.

## ملحق (2026-08-13) — إخفاء خيار "الصيانة العامة" من حوار الفرز لدوره

### توضيح إضافي من صاحب المشروع

بعد التنفيذ الأول، طلب توضيح: لا يريد أن يُخيَّر مدير الإنشاءات والمشتريات بين الجهتين عند
فرز بلاغه الشخصي — يجب أن يظهر له **خيار "قسم الإنشاءات" وحده**، لا خيار "الصيانة العامة"
إطلاقًا. لا معنى منطقي لتوجيهه بلاغه الشخصي لجهة ليست جهته أصلًا.

### الحل المنفذ

في `client/src/pages/tickets/TicketDetail.tsx`، حوار الفرز المتعدد (نفس الحوار الموصوف
أعلاه، بلا أي ملف آخر): أُضيف `.filter(...)` على مصفوفة الجهتين الثابتة قبل `.map(...)`،
يستبعد خيار "الصيانة العامة" حصرًا حين يكون الفارز الحالي `CONSTRUCTION_PROCUREMENT_MANAGER`:

```ts
[
  { key: GENERAL, label: "الصيانة العامة", mgrs: generalManagers },
  { key: CONSTRUCTION, label: "قسم الإنشاءات", mgrs: constructionManagers },
]
  .filter(({ key }) =>
    role !== APP_ROLE.CONSTRUCTION_PROCUREMENT_MANAGER ||
    key === MAINTENANCE_RESPONSIBLE_DEPARTMENT.CONSTRUCTION
  )
  .map(...)
```

بقية الأدوار المسموح لها بفتح هذا الحوار (مدير الصيانة العامة، الأدمن، المالك) ترى الخيارين
معًا كما كانا — الشرط يستثني دوره تحديدًا فقط، لا يُقيِّد أي دور آخر.

الخيار يبقى **صندوق اختيار يدوي** (لا يُختار تلقائيًا) — طابق صياغة الطلب الحرفية "السماح
باختيار قسم الإنشاءات"، لا فرضه بلا تدخل من المستخدم.

**لا تعديل على السيرفر في هذا الملحق.** الحارس `assertConstructionManagerOwnTicketForTriage`
والقيد على `resolveResponsibleManagerId` (الذي أصلًا يشترط أن يكون المسؤول عن جهة الإنشاءات
من دور `CONSTRUCTION_PROCUREMENT_MANAGER` تحديدًا) كافيان لمنع أي محاولة توجيه فعلية لجهة
الصيانة العامة حتى لو تلاعب أحد بطلب الشبكة مباشرة متجاوزًا هذا الفلتر بالواجهة — هذا الملحق
تحسين تجربة مستخدم فقط، لا طبقة أمان جديدة.

**لا Migration.**
