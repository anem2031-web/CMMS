# إصلاح دورة البلاغ — المسار B (شراء مواد ثم إصلاح)

تاريخ التنفيذ: 2026-08-03

## الهدف

إغلاق جميع طرق تجاوز دورة الشراء في المسار B، وجعل طلبات الشراء الفعلية هي المصدر الوحيد لحالة شراء مواد البلاغ، ثم السماح ببدء الإصلاح فقط بعد تسليم جميع المواد الفعالة إلى الفني.

## دورة العمل المعتمدة بعد الإصلاح

```text
اعتماد نتيجة الفحص
→ اختيار المسار B
→ work_approved
→ إنشاء طلب شراء واحد مرتبط بالبلاغ
→ pending_review / needs_purchase
→ pending_estimate / purchase_pending_estimate
→ pending_accounting / purchase_pending_accounting
→ pending_management / purchase_pending_management
→ approved / purchase_approved
→ شراء الأصناف (جزئي أو كامل)
→ وصول المواد إلى المستودع: يبقى البلاغ purchased
→ تسليم جميع المواد الفعالة إلى الفني: received_warehouse
→ الضغط على «بدء الإصلاح»: in_progress
→ كتابة ملاحظات الإصلاح وإرفاق صورة بعد الإصلاح
→ ready_for_closure
→ إغلاق مدير الجهة: closed
```

## التعديلات المنفذة

### 1. استعادة شاشة إنشاء طلب الشراء

أعيدت شاشة إنشاء طلب الشراء الفعلية في:

```text
client/src/pages/purchase/CreatePurchaseOrder.tsx
```

وتتحقق الواجهة من أن البلاغ المرتبط:

- مساره `B`.
- في الحالة الصحيحة لإنشاء الطلب.
- لم يتجاوز دورة الشراء.

الحماية الأساسية موجودة أيضًا في الخادم، لذلك لا يعتمد المنع على إخفاء الزر فقط.

### 2. طلب شراء مرتبط واحد نشط

لا يمكن إنشاء طلب شراء مرتبط جديد إذا وجد طلب نشط للبلاغ نفسه. تشمل الحالات النشطة المسودة والمراجعة والتسعير والاعتمادات والتنفيذ والاستلام.

الطلبات التاريخية المتعددة الموجودة سابقًا لا تُحذف. عند وجود أكثر من طلب قديم، تُحسب حالة البلاغ من جميع الطلبات الفعالة، ولا يسمح طلب متقدم بتجاوز طلب آخر ما زال في مرحلة أسبق.

### 3. الصلاحيات والنطاق

إنشاء طلب شراء مرتبط ببلاغ المسار B متاح فقط للأدوار التالية، مع تطبيق نطاق الجهة المسؤولة عن البلاغ:

- مدير الصيانة.
- مدير الصيانة العامة والتشغيل.
- مدير الإنشاءات والمشتريات للبلاغات المحولة إليه.
- المسؤول `admin`.
- المالك `owner`.

لا يكفي أن يكون المستخدم مسجل الدخول؛ يتحقق الخادم من الدور والمسار والحالة ونطاق البلاغ.

### 4. طلبات الشراء هي مصدر الحقيقة

أضيفت مزامنة مركزية في:

```text
server/routers/purchase/ticket-purchase-workflow.ts
shared/pathBPurchaseWorkflow.ts
```

تُشتق حالة البلاغ من حالة طلب الشراء وأصنافه بعد كل إجراء مؤثر، ومنها:

- إرسال الطلب للمراجعة.
- مراجعة الأصناف.
- التسعير.
- اعتماد الحسابات.
- اعتماد الإدارة.
- شراء الأصناف أو إلغاؤها.
- استلام المستودع.
- التسليم للفني.
- الإعادة للمراجعة أو الرفض أو الإغلاق أو الحذف المسموح.

لا توجد تحديثات مباشرة لحالة البلاغ داخل راوتر طلبات الشراء خارج المزامنة المركزية.

### 5. تعطيل محرك الشراء القديم داخل البلاغات

عُطلت إجراءات البلاغ القديمة التي كانت تغيّر حالة البلاغ من دون طلب شراء فعلي، ومنها:

```text
assignTechnician
startWork
submitEstimate
submitToAccounting
submitToManagement
approvePurchase
executePurchase
completePurchase
receiveInWarehouse
```

تعيد هذه الإجراءات خطأ واضحًا يوجه إلى دورة `purchase_orders` المعتمدة.

كما مُنعت إجراءات الإغلاق القديمة (`markRepaired` و`markVerified` و`finalClose`) من العمل على المسارات `A/B/C`، وبقيت فقط للتوافق مع البلاغات التاريخية التي لا تحمل مسار صيانة.

### 6. منع بدء الإصلاح قبل التسليم للفني

وصول المواد إلى المستودع لا يفتح زر بدء الإصلاح، ولا يحول البلاغ إلى مرحلة التنفيذ.

لا يصبح البلاغ `received_warehouse` إلا بعد أن تصبح جميع الأصناف الفعالة:

```text
delivered_to_requester
```

ويعيد الخادم فحص أصناف الطلب فعليًا عند الضغط على «بدء الإصلاح»، حتى لو كانت حالة البلاغ قد عُدلت يدويًا أو كانت الواجهة قديمة.

### 7. منع تجاوز زر بدء الإصلاح

لا يظهر نموذج إتمام إصلاح المسار B عند `received_warehouse`. يظهر فقط بعد الضغط على «بدء الإصلاح» وتحول البلاغ إلى:

```text
in_progress
```

كما يمنع الخادم إجراء الإكمال قبل هذه الحالة.

### 8. إلزام توثيق الإصلاح

لا يتفعل زر «إتمام العمل — إرسال للإغلاق» إلا بعد:

- كتابة ملاحظات إصلاح غير فارغة.
- إرفاق صورة بعد الإصلاح.

ويتحقق الخادم من الشرطين مرة أخرى قبل حفظ `ready_for_closure`.

### 9. حماية الإغلاق

إغلاق المسار B متاح فقط عندما:

- الحالة `ready_for_closure`.
- المسار `B`.
- ملاحظات الإصلاح محفوظة.
- صورة ما بعد الإصلاح محفوظة.
- المستخدم مدير مخول ضمن نطاق البلاغ.

إجراء إغلاق المشرف مخصص للمسار A فقط. ولا تستطيع إجراءات الإغلاق القديمة إغلاق مسار B.

### 10. منع إعادة فتح البلاغ بتحديث متأخر

بعد دخول البلاغ إلى التنفيذ أو الإغلاق، لا تستطيع أي حركة متأخرة في طلب شراء قديم إعادته إلى مرحلة شراء سابقة. الحالات المحمية تشمل:

```text
in_progress
ready_for_closure
repaired
verified
closed
requester_confirmed
```

### 11. رفض أو إلغاء جميع الأصناف

عندما لا يبقى طلب شراء فعال أو لا يبقى صنف فعال، تعود حالة البلاغ إلى:

```text
work_approved
```

حتى يستطيع المدير إنشاء طلب بديل بدل بقاء البلاغ عالقًا في `needs_purchase`.

## الاختبارات والتحقق

أضيفت أو حُدثت اختبارات للتحقق من:

- اشتقاق حالة البلاغ من جميع طلبات الشراء المرتبطة.
- عدم بدء الإصلاح عند وصول المواد إلى المستودع فقط.
- بدء الإصلاح بعد تسليم جميع المواد إلى الفني.
- إخفاء طلب شراء جديد عند وجود طلب نشط.
- إخفاء نموذج الإكمال حتى الضغط على بدء الإصلاح.
- إلزام الملاحظات والصورة.
- تعطيل دورة الشراء والإغلاق القديمة.
- استعادة شاشة إنشاء طلب الشراء الفعلية.

تم اجتياز فحص التحويل النحوي للملفات المتأثرة، واختبارات منطق المسار B النقية، وفحوص عقود الربط النصية. لم تُشغّل مجموعة `vitest` الكاملة في بيئة التجهيز لأن التبعيات الكاملة غير متاحة؛ لذلك يجب تشغيل الأمر التالي داخل بيئة المشروع المثبتة قبل النشر:

```bash
npm test
npm run check
```

## اختبار تشغيلي مقترح قبل الإنتاج

1. إنشاء بلاغ جديد واعتماد الفحص واختيار B.
2. التأكد أن «بدء الإصلاح» غير ظاهر وأن «طلب شراء جديد» ظاهر للمدير المخول فقط.
3. إنشاء الطلب والتأكد من اختفاء زر طلب جديد.
4. تنفيذ المراجعة والتسعير والاعتمادات والشراء.
5. استلام المواد في المستودع والتأكد أن زر بدء الإصلاح ما زال مخفيًا.
6. تسليم جميع المواد للفني والتأكد من ظهور زر بدء الإصلاح.
7. الضغط على بدء الإصلاح والتأكد من ظهور نموذج الإكمال.
8. التأكد أن زر الإكمال معطل دون ملاحظات وصورة.
9. إرفاقهما وإرسال البلاغ للإغلاق.
10. إغلاق البلاغ بحساب مدير الجهة والتأكد أن المشرف لا يستطيع إغلاق المسار B.
