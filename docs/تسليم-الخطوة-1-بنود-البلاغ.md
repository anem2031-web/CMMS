# تسليم الخطوة 1 — بنود البلاغ (الأساس)

## ما الذي تغيّر فعليًا

أُضيف مكان تخزين جديد اسمه **"بنود البلاغ"**، وكل بلاغ موجود عندك الآن أصبح له **بند واحد** منسوخ من
بياناته الحالية تلقائيًا.

**لم يتغيّر أي شيء تراه أو تستخدمه.** الفرز كما هو، اختيار المسار كما هو، طلبات الشراء كما هي،
كل الشاشات كما هي، وكل التقارير كما هي. هذه الخطوة تُجهّز الأرضية فقط، ولا تُفعّل أي سلوك جديد.

## خطوات التطبيق والتجربة

### 1. تطبيق الترحيل على قاعدة البيانات

نفّذ محتوى الملف:

```
drizzle/migrations/2026_08_08_ticket_items_multi_task.sql
```

الملف آمن ويمكن تشغيله أكثر من مرة دون أن يُكرّر البيانات.

### 2. التحقق أن كل بلاغ حصل على بند

يجب أن يكون الرقمان **متساويين تمامًا**:

```sql
SELECT COUNT(*) AS عدد_البلاغات FROM tickets;
SELECT COUNT(*) AS عدد_البنود   FROM ticket_items;
```

### 3. التحقق من عدم وجود بلاغ بلا بند

يجب أن تكون النتيجة **صفرًا**:

```sql
SELECT COUNT(*) FROM tickets t
WHERE NOT EXISTS (SELECT 1 FROM ticket_items ti WHERE ti.ticketId = t.id);
```

### 4. مقارنة بلاغ حقيقي ببنده (البلاغ الذي فحصناه سابقًا)

يجب أن تتطابق كل القيم بين السطرين:

```sql
SELECT id, status, maintenancePath, assignedToId, justification
FROM tickets WHERE ticketNumber = 'MT-2026-00145';

SELECT ticketId, itemNumber, status, maintenancePath, assignedToId,
       justification, isLegacySingleItem
FROM ticket_items WHERE ticketId = 1800008;
```

المتوقع: بند واحد، رقمه 1، حالته `work_approved`، مساره `C`، وعلامة `isLegacySingleItem` تساوي 1.

### 5. تشغيل الفحوصات

```
npm run check
npm test
```

### 6. التجربة العملية على النظام

- افتح أي بلاغ وتصفّحه كالمعتاد → **يجب ألا تلاحظ أي فرق إطلاقًا**.
- أنشئ بلاغًا جديدًا وافرزه كالمعتاد → يعمل كما كان تمامًا.
- جرّب حذف بلاغ تجريبي → يجب أن يُحذف بنجاح (هذه أهم نقطة اختبار في هذه الخطوة).

## نقطة انتباه مهمة

البلاغات الجديدة التي تُنشأ **بعد** تطبيق هذا الترحيل **لن يُنشأ لها بند تلقائيًا بعد**، لأن ربط الإنشاء
بالبنود يأتي في الخطوة التالية. هذا مقصود ولا يسبب أي ضرر: البلاغ الجديد يعمل بشكل كامل وطبيعي من
أعمدته الحالية تمامًا كما هو الوضع اليوم.

إن أردت لاحقًا معالجة البلاغات التي أُنشئت في هذه الفترة الفاصلة، يكفي إعادة تشغيل نفس ملف الترحيل مرة
أخرى — سيلتقط البلاغات الجديدة فقط دون المساس بما سبق.

## التراجع عند الحاجة

طالما لم تبدأ الخطوة التالية بعد، التراجع بسيط وبلا أي فقدان بيانات (لأن كل البيانات لا تزال موجودة في
جدول البلاغات نفسه كما كانت):

```sql
-- تأكد أولًا أن النتيجة صفر (لا يوجد بند أنشأه مستخدم فعليًا)
SELECT COUNT(*) FROM ticket_items WHERE isLegacySingleItem = 0;

DROP TABLE ticket_items;
```

ثم التراجع عن تعديلات الملفات الستة المذكورة أعلاه.
