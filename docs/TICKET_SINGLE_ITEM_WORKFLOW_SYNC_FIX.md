# إصلاح مزامنة البلاغ الأحادي/الفرعي مع `ticket_items` في مسارات A/B/C

**التاريخ:** 2026-08-12

## ملخص المشكلة

أثناء اختبار البلاغات الفرعية ظهر أن اختيار مسار الصيانة على البلاغ ينجح ظاهريًا في واجهة البلاغ، لكن بعض الشاشات اللاحقة لا ترى البلاغ. المثال الأوضح كان المسار C: البلاغ يظهر داخل `tickets` بأنه `work_approved / C`، لكنه لا يظهر في شاشة تجهيز الصيانة الخارجية للمستودع ولا للإدارة/المالك.

السبب لم يكن صلاحيات الأدوار ولا استعلام شاشة المستودع. الاستعلام يعتمد عمدًا على `ticket_items` كمصدر حقيقة لوحدة التنفيذ، بينما إجراء البلاغ الأحادي كان يحدّث رأس `tickets` فقط.

## الدليل الذي كشف المشكلة

في اختبار البلاغ الأب `MT-2026-00252` كانت البلاغات الفرعية الثلاثة تحمل حالات صحيحة في رأس البلاغ، لكن بند التنفيذ الوحيد بقي قديمًا:

- `MT-2026-00252-01`: رأس البلاغ وصل إلى `requester_confirmed` والمسار `B`، بينما البند بقي `under_inspection` وبدون `maintenancePath`.
- `MT-2026-00252-02`: رأس البلاغ وصل إلى `requester_confirmed` والمسار `A`، بينما البند بقي `under_inspection` وبدون `maintenancePath`.
- `MT-2026-00252-03`: رأس البلاغ أصبح `work_approved / C`، بينما البند بقي `under_inspection` وبدون `maintenancePath`.

إذًا الخلل عام في مزامنة البلاغ الأحادي/الفرعي مع بند التنفيذ، وليس خاصًا بالمسار C. أثر C ظهر أولًا لأن شاشة الصيانة الخارجية تقرأ `ticket_items.maintenancePath/status` مباشرة.

## السبب الجذري

واجهة تفاصيل البلاغ تستخدم إجراءات مستوى **رأس البلاغ** عندما يكون عدد البنود `<= 1`، مثل `approveWork`, `startRepair` وإجراءات الإغلاق. هذه الإجراءات القديمة كانت تغيّر `tickets.status` و`tickets.maintenancePath` وحقول التنفيذ ذات الصلة، لكنها لا تحرك سجل `ticket_items` الوحيد معها.

في المقابل، البلاغ متعدد البنود يستخدم إجراءات مستوى البند مثل `approveWorkForItem` و`startRepairForItem`، وهذه كانت تحدّث `ticket_items` مباشرة ثم تعكس البند الأول على رأس البلاغ عند الحاجة.

النتيجة كانت اتجاه مزامنة واحد فقط:

```text
بلاغ متعدد البنود: ticket_items  → tickets   ✅
بلاغ أحادي/فرعي:   tickets       → ticket_items ❌
```

## الحل المنفذ

أضيفت الدالة المشتركة:

`server/_core/db/tickets.ts::syncSingleTicketItem(ticketId, data)`

سلوكها مقصود ومحافظ:

1. تجلب بحد أقصى بندين للبلاغ.
2. إذا كان عدد البنود **واحدًا بالضبط**، تحدّث هذا البند بالحقول المطلوبة.
3. إذا كان البلاغ بلا بنود أو متعدد البنود، لا تفعل شيئًا.
4. لا تختار البند الأول عشوائيًا في البلاغ متعدد البنود، ولا تنشئ بندًا مفقودًا.

ثم رُبطت المزامنة بإجراءات رأس البلاغ التي تحرك دورة التنفيذ الأحادية:

- اعتماد A/B/C: `work_approved` + `maintenancePath` + بيانات الاعتماد.
- بدء التنفيذ: `in_progress`.
- إكمال/رفع نتيجة التنفيذ: `repaired` أو `ready_for_closure` مع صورة/ملاحظات/مواد عند وجودها.
- الإغلاق: `closed` + `closedAt`.
- تأكيد صاحب البلاغ: `requester_confirmed`.
- مسار B القديم: `needs_purchase`، وكذلك مزامنة الحالات المشتقة من دورة طلب الشراء عبر `syncPathBTicketFromTicketId`.

## لماذا لم نعدل شاشة الصيانة الخارجية؟

شاشة الصيانة الخارجية صحيحة في اعتمادها على `ticket_items` لأن البند هو وحدة التنفيذ الفعلية. إضافة fallback إلى `tickets` كانت ستخفي عدم اتساق البيانات بدل إصلاحه، وقد تعيد مشاكل عند وجود عدة بنود مستقلة في البلاغ نفسه.

بعد الإصلاح، عند اختيار C لبلاغ أحادي أو بلاغ فرعي، تصبح البيانات مثلًا:

```text
tickets:      status = work_approved, maintenancePath = C
ticket_items: status = work_approved, maintenancePath = C
```

فتلتقطه شاشة تجهيز الصيانة الخارجية طبيعيًا.

## النطاق

يشمل الإصلاح:

- البلاغ الأحادي العادي.
- البلاغ الفرعي `workflowModel = sub_ticket` لأنه يملك وحدة تنفيذ واحدة ويدخل Workflow مستقلًا.
- مسارات A وB وC ومراحل التنفيذ/الإغلاق المرتبطة بإجراءات رأس البلاغ.

لا يغير الإصلاح منطق البلاغ متعدد البنود؛ إجراءاته الخاصة بالبند تبقى هي مصدر الحقيقة لكل بند مستقل.

## قاعدة البيانات

**لا يوجد Migration أو DDL لهذا الإصلاح.** التغيير برمجي فقط.

مهم: الإصلاح يمنع إنشاء عدم اتساق جديد، لكنه لا يعدّل تلقائيًا سجلات قديمة أصبحت غير متزامنة قبل نشره. الحالات القديمة مثل `MT-2026-00252-01/-02/-03` تحتاج مصالحة بيانات لمرة واحدة إذا كان المطلوب استمرار اختبارها بدل إنشاء بلاغ اختبار جديد.

## اختبار تشغيلي مقترح

1. **A / بلاغ أحادي أو فرعي:** اعتماد A → بدء الإصلاح → جاهز للإغلاق → الإغلاق → تأكيد صاحب البلاغ. بعد كل خطوة يجب أن تتطابق `tickets.status` و`ticket_items.status`، وأن يكون `maintenancePath = A` في الاثنين.
2. **B:** اعتماد B → إنشاء/إكمال دورة الشراء → استلام المواد → بدء التنفيذ → جاهز للإغلاق → الإغلاق. يجب أن تتحرك حالات الشراء في رأس البلاغ والبند الوحيد معًا.
3. **C:** اعتماد C → يجب أن يظهر فورًا في شاشة تجهيز الصيانة الخارجية للأدوار المخولة. بعد الخروج/العودة/التسليم/إعادة التركيب/الإغلاق يجب أن تبقى حالة البند والرأس متوافقة.
4. **بلاغ متعدد البنود:** اعتماد مسارات مختلفة لعدة بنود والتأكد أن `syncSingleTicketItem` لا يلمس أي بند؛ كل بند يبقى مستقلًا عبر إجراءات `*ForItem`.
