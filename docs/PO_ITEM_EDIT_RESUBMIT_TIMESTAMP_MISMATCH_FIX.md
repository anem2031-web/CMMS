# رفض "حفظ وإرسال" لتعديل الصنف المُعاد للمنشئ — خطأ تنسيق لا تعارض حقيقي

تاريخ التنفيذ: 2026-08-13

## 1. المشكلة المبلَّغ عنها

بعد أن يطلب المندوب مراجعة صنف (`needs_item_revision`)، يفتح منشئ الطلب تعديله ويضغط
«حفظ وإرسال»، فتظهر دائمًا: **«تم تعديل الصنف بواسطة مستخدم آخر، قم بتحديث الصفحة»**،
ولا يُقبل الحفظ إطلاقًا — لا أحيانًا، بل في كل مرة.

## 2. السبب الجذري

القفل التفاؤلي (`lastKnownUpdatedAt`) في `editItem` و`editAndResubmitReturnedItem`
(`purchase-orders.router.ts`) يقارن نصًّا بنص:

```ts
String(oldItem.updatedAt) !== String(input.lastKnownUpdatedAt)
```

`purchaseOrderItems.updatedAt` معرَّف بـ`mode: 'string'` في `drizzle/schema.ts` — القيمة
الواصلة من قاعدة البيانات سلسلة MySQL خام مثل `"2026-08-13 10:30:00"`، بلا تحويل لكائن
`Date` وبلا منطقة زمنية، ولا يمر عليها superjson (مُفعَّل كمحوِّل tRPC) لأنه لا يتعرّف إلا
على كائنات `Date` الحقيقية.

لكن `getLastKnownUpdatedAt` بالواجهة (`PurchaseOrderDetail.tsx`) كانت تُحوّل هذه السلسلة
الخام إلى `Date` ثم `.toISOString()` قبل الإرسال: `"2026-08-13T10:30:00.000Z"`.

مقارنة `"2026-08-13 10:30:00"` بـ`"2026-08-13T10:30:00.000Z"` **لن تتطابق أبدًا مهما كان
التوقيت الفعلي مطابقًا تمامًا** — فاصل `T` مفقود بإحداهما، ولاحقة `.000Z` زائدة بالأخرى،
واحتمال فارق منطقة زمنية إضافي بين متصفح المستخدم وسيرفر Node عند تحليل سلسلة بلا منطقة
زمنية صريحة. هذا يفسّر الفشل التام: القفل التفاؤلي لم يكن يكتشف تعارضًا حقيقيًا بين
مستخدمين قط — كان يقارن تمثيلين مختلفين شكليًا للقيمة نفسها، فيفشل دومًا بالتصميم.

هذا النمط (`lastKnownUpdatedAt`) غير مستخدَم في أي مكان آخر بالمشروع (تحقَّق بالبحث
الشامل)، فلا توجد سابقة "تعمل فعليًا" ليُقاس عليها — يبدو أنه لم يُختبر مقابل قاعدة بيانات
حقيقية قبل هذا البلاغ.

## 3. الحل المنفذ

تعديل واحد فقط، في `getLastKnownUpdatedAt` بـ`PurchaseOrderDetail.tsx`: القيمة تُعامَل
كرمز مطابقة خام (شبيه بـETag) لا كتاريخ يحتاج تحليلًا وإعادة تنسيق. تُمرَّر كما وصلت من
السيرفر حرفيًا بلا أي تحويل عبر `Date`:

```ts
const getLastKnownUpdatedAt = (item: any): string | undefined => {
  if (item?.updatedAt === null || item?.updatedAt === undefined) return undefined;
  return String(item.updatedAt);
};
```

بهذا يصبح الطرفان (قيمة السيرفر الحالية وقيمة العميل المرسَلة) نفس السلسلة الحرفية بلا أي
إعادة تنسيق على أي جانب، فتتطابقان فعليًا عند عدم وجود تعديل من طرف آخر، ويكتشف الحارس
تعارضًا حقيقيًا فقط عند تغيّر القيمة فعلًا في القاعدة (`onUpdateNow()` عند أي تعديل حقيقي).

**لم يُعدَّل الحارس بالسيرفر إطلاقًا** — المقارنة النصية هناك كانت صحيحة أصلًا؛ الخلل كان
حصرًا في تنسيق القيمة المُرسَلة من الواجهة.

## 4. قاعدة البيانات

**لا Migration ولا DDL.** تعديل داخل دالة واجهة واحدة فقط.

## 5. قيود معروفة / خارج النطاق

- **دقة `updatedAt` بالثانية** (لا كسور ثانية) — تعديلان حقيقيان خلال نفس الثانية قد لا
  يُكتشَف تعارضهما نظريًا. قيد معماري قائم أصلًا بتصميم القفل التفاؤلي نفسه، لم يُدخله هذا
  الإصلاح ولم يُعالَج لأنه خارج نطاق البلاغ (الفشل التام في كل مرة، لا نافذة تزامن ضيقة).
- لم يُختبر البناء (`tsc`) في بيئة التنفيذ لعدم توفر `node_modules`؛ التحقق كان بتتبع تدفق
  القيمة من `drizzle/schema.ts` عبر السيرفر وحتى الواجهة، ومطابقة توازن الأقواس آليًا.
