# فشل رفع الصورة المتقطع في صفحة الصيانة الخارجية (وفي `/api/upload` عمومًا)

تاريخ التنفيذ: 2026-08-12

## 1. المشكلة المبلَّغ عنها

عند «تجهيز الأصل للصيانة الخارجية» في `/external-maintenance`، رفع صورة الأصل **ينجح أحيانًا ويفشل
أحيانًا** بلا نمط واضح للمستخدم.

## 2. السبب الجذري

`ExternalMaintenanceWarehouseTab.tsx` كانت الصفحة الوحيدة التي ترفع بطريقة بدائية، بينما بقية الصفحات
تستخدم `useOfflineUpload` (ضغط + presigned URL + fallback + طابور offline):

```ts
const response = await fetch("/api/upload", { method: "POST", body: formData });
const data = await response.json();
```

بلا ضغط، بلا مهلة، بلا إعادة محاولة، وبلا حماية من رد غير JSON. الأسباب المجتمعة للتذبذب:

1. **الحجم:** صور الجوال 5–15MB تُرسل كما هي؛ صورة صغيرة تنجح وأخرى تسقط على المهلة أو 413.
2. **HEIC (آيفون):** النسخ الجاهزة من `sharp` لا تفك ترميز HEIC/HEIF، بينما `fileFilter` كان **يسمح**
   بمرور `image/heic` — فيرمي `sharp` استثناءً ويعود 500. نفس الجهاز: JPG من المعرض ينجح، HEIC من
   الكاميرا يفشل. هذا أرجح سبب لشكل العطل الموصوف.
3. **mimetype مبهم:** أندرويد/iOS يرسلان أحيانًا `""` أو `application/octet-stream` لصور سليمة، فيرفضها
   `fileFilter`.
4. **أخطاء multer تتجاوز `try/catch`** لأنها تقع في الـmiddleware لا في الـhandler، فتصل كـ500 عام.
5. **رفع S3 بمحاولة واحدة** نحو iDrive e2 بلا retry — أي تعثر شبكي عابر = فشل نهائي.
6. **حقل الملف لا يُصفَّر:** بعد أي فشل، إعادة اختيار **نفس** الصورة لا تُطلق `onChange` إطلاقًا، فيبدو
   الزر وكأنه توقف — وهذا وحده يجعل العطل يبدو عشوائيًا.

> **ملاحظة توثيقية:** تحليل أولي زعم أن سجلات `.manus-logs/networkRequests.log` تُظهر طلبات `/api/upload`
> رجعت 500 في صفحات أخرى. **الفحص نفى ذلك:** 91 طلبًا مسجلًا كلها tRPC، صفر طلبات رفع، صفر ردود 500.
> كل ورود كلمة "upload" في السجل هو مفتاح ملف مخزَّن (`/api/media?key=cmms%2Fuploads%2F…`) داخل أجسام
> الردود. الجلسة المسجَّلة لم يُرفع فيها ملف أصلًا، فالسجلات لا تصلح دليلًا هنا. الأسباب أعلاه مستنتجة
> من الكود لا من السجل.

## 3. ما نُفِّذ

### الواجهة — `client/src/pages/purchase/ExternalMaintenanceWarehouseTab.tsx`

- ضغط الصورة داخل المتصفح عبر `compressImage` الموجودة أصلًا في `hooks/useOfflineUpload` (5–15MB → ~200–400KB).
- مهلة 90 ثانية عبر `AbortController`، وإعادة محاولة واحدة لأخطاء الشبكة العابرة (`TypeError`) فقط.
- قراءة آمنة للرد: `response.text()` ثم `JSON.parse` داخل `try`، مع رسائل عربية لكل رمز حالة
  (401 جلسة منتهية / 413 حجم / 415 صيغة / 429 حد الطلبات).
- كشف الصور بالامتداد عند غياب الـmimetype، وحارس حجم 15MB وحجم صفري.
- `e.target.value = ""` بعد كل اختيار في الحقول الثلاثة (قبل/بعد/تقرير الورشة).

### السيرفر — `server/_core/index.ts`

- `fileFilter` يقبل الامتداد عند `mimetype` فارغ أو `application/octet-stream`.
- `uploadSingleFile` — غلاف يحوّل أخطاء multer إلى 413/415 برسالة مفهومة بدل 500 عام.
- `sharp` داخل `try/catch`: عند HEIC تُرجع 415 برسالة صريحة (غيّر إعداد الكاميرا إلى JPEG)، وعند فشل
  آخر يُرفع الملف الأصلي بدل إسقاط العملية — نفس نمط `transcodeVideoToCompatibleMp4` القائم.
- `storagePutWithRetry` — محاولة ثانية بعد 700ms قبل الاستسلام.

## 4. قاعدة البيانات

**لا Migration ولا DDL.** تغيير كود فقط.

## 5. قيود معروفة / خارج النطاق

- الصفحة لا تزال ترفع عبر `/api/upload` بدل مسار presigned المباشر. توحيدها مع `useOfflineUpload`
  (للاستفادة من الطابور دون اتصال) تغيير أوسع تُرك عمدًا لمهمة منفصلة.
- صفحات `DropZone` ترفع أيضًا بلا ضغط (لها حارس 10MB فقط)، فتستفيد من إصلاحات السيرفر أعلاه لكنها لا
  تزال ترسل الملف الأصلي كاملًا.
- **لم يُختبر البناء (`tsc`)** في بيئة التنفيذ لعدم توفر `node_modules`؛ التحقق كان بالقراءة.

## ملحق (2026-08-13) — تعطّل الرفع كليًا بسبب حرف واحد في `S3_ACCESS_KEY`

**حادثة منفصلة تمامًا عن العطل المتقطع أعلاه**، لكنها كشفت غياب فحص مهم.

### ما حدث
توقف رفع الملفات في **كل** النظام بخطأ متكرر:
`InvalidAccessKeyId: The Access Key Id you provided does not exist in our records. 403`

### التشخيص (بالاستبعاد المتسلسل)
| الفرضية | كيف استُبعدت |
|---|---|
| المفتاح منتهٍ/محذوف | ظاهر ونشط في لوحة iDrive |
| المنطقة/الـendpoint خطأ | `Frankfurt-2` = `eu-central-1` حرفيًا، مطابق للوحة |
| المستودع مفقود | `cmms-uploads` موجود بـ4,902 كائن |
| متغير بيئة على مستوى Windows يطغى | `echo %S3_ACCESS_KEY%` أرجع الاسم حرفيًا (غير معرّف) |
| تكرار المتغير في `.env` | `findstr /N` أظهر سطرًا واحدًا لكل متغير |
| قيمة مشوّهة (مسافة/`\r`/ترميز) | `JSON.stringify(process.env.S3_ACCESS_KEY)` أظهرها نظيفة |
| خلل في كود المشروع | `ListBucketsCommand` مباشرة عبر AWS SDK (خارج المشروع كليًا) فشل بنفس الخطأ |
| عطل في خدمة iDrive | حساب اختباري جديد نجح فورًا بنفس الـendpoint والمنطقة |

### السبب الفعلي
مقارنة المفتاح المنسوخ من اللوحة بما في `.env` أظهرت اختلاف **حرف واحد**:
اللوحة `…XTJf` **`i`** `PaBH` مقابل الملف `…XTJf` **`j`** `PaBH`.

خطأ نسخ بصري. الأحرف `i/j` و`0/O` و`1/l/I` متشابهة في خط لوحة التحكم.

### الدرس والإصلاح
`JSON.stringify` يثبت أن القيمة **نظيفة**، لا أنها **صحيحة** — تمييز مهم أضاع وقتًا في التشخيص.

أُضيف `server/_core/storage.ts::checkStorageHealth()` ويُستدعى من `index.ts` داخل
`server.listen()` مباشرة. ينفّذ `HeadBucketCommand` (أخف عملية: تتحقق من المفتاح والسر
والمنطقة والمستودع والصلاحية دفعة واحدة بلا نقل بيانات) ثم يطبع:

- نجاح: `[Storage] ✅ متصل بالمستودع "cmms-uploads" على …`
- فشل: سبب مترجَم وإجراء محدد لكل حالة (`InvalidAccessKeyId` / `SignatureDoesNotMatch` /
  `NoSuchBucket` / `AccessDenied`)، مع طول المفتاح وأول/آخر 4 أحرف منه (بلا كشف القيمة كاملة).

**⚠️ لا يوقف السيرفر** — التخزين ليس شرطًا لتشغيل بقية النظام؛ يطبع ويكمل.

### تنبيه أمني مسجَّل
أثناء التشخيص رُفع ملف `.env` كاملًا في محادثة، فانكشفت `JWT_SECRET` و`DB_PASSWORD` و
`ANTHROPIC_API_KEY` و`ADMIN_SEED_PASSWORD` ومفاتيح VAPID. **يجب تدوير هذه الأسرار جميعًا**؛
أخطرها `JWT_SECRET` (يسمح بتزوير جلسة أي مستخدم بما فيهم المالك بلا كلمة مرور).
