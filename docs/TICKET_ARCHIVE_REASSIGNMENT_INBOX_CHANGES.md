# توثيق تنظيم وثائق البلاغ وإعادة إسناد الفني وصندوق الإنشاءات

**التاريخ:** 2026-08-03  
**النطاق:** واجهة البلاغات، صندوق البلاغات، صلاحيات الوثائق، إعادة إسناد الفني، وملفات PDF الخاصة بالبلاغ.  
**تغييرات قاعدة البيانات:** لا توجد.

## 1. توضيح بيانات نتيجة الفحص

تم استبدال العبارات المختصرة بعبارات أوضح:

- **نسخة نتيجة الفحص رقم 1:** رقم مراجعة نتيجة الفحص داخل البلاغ. يزيد عند إعادة النتيجة للتصحيح ثم إرسال نسخة جديدة.
- **مسودة محفوظة — لم تُرسل للمراجعة:** النتيجة محفوظة، لكنها لم تنتقل بعد إلى مدير الجهة لاعتمادها.
- **من قام بالفحص ميدانيًا:** المستخدم الذي نفّذ المعاينة الفعلية في الموقع.
- **من أدخل النتيجة في النظام:** المستخدم الذي كتب وسجّل البيانات داخل التطبيق.

قد يكون الشخصان نفس المستخدم، وقد يكون الفني هو منفذ الفحص والمدير هو مدخل البيانات.

## 2. تعديل بيانات البلاغ

زر **تعديل البلاغ** يظهر فقط عندما تكون حالة البلاغ:

```text
pending_triage
```

بمجرد اعتماد الفرز وانتقال البلاغ إلى أي مرحلة لاحقة يختفي الزر من:

- قائمة البلاغات.
- صفحة تفاصيل البلاغ.

هذا التنظيم يطبق على جميع الأدوار. لا يسمح التغيير بعد بدء الفرز عبر الواجهة.

## 3. التقرير الأرشيفي للبلاغ

تحولت وظيفة زر **تحميل التقرير** إلى **تحميل التقرير الأرشيفي**.

### وقت الظهور

لا يظهر إلا بعد إغلاق البلاغ، في الحالتين:

```text
closed
requester_confirmed
```

### الأدوار المخولة

- `maintenance_manager` — مدير الصيانة.
- `construction_procurement_manager` — مدير الإنشاءات والمشتريات.
- `general_maintenance_manager` — مدير الصيانة العامة والتشغيل.
- `admin` — مدير النظام.
- `owner` — المالك.

### محتوى الوثيقة

الوثيقة الأرشيفية تجمع بيانات البلاغ من إنشائه حتى إغلاقه، وتشمل حسب البيانات المتاحة:

- بيانات البلاغ والموقع ومقدم البلاغ.
- التصنيف والأولوية والجهة المسؤولة.
- الفني المسند إليه.
- نتائج الفحص ومراجعاتها ومنفذ الفحص ومدخل البيانات.
- سجل الحالات والإجراءات والتواريخ والملاحظات.
- مسار الصيانة والتنفيذ.
- طلبات الشراء المرتبطة.
- المرفقات والصور المتاحة.
- بيانات الإغلاق.

المسار المستخدم:

```text
GET /api/tickets/:id/pdf?document=archive
```

## 4. طباعة المهمة

زر **طباعة المهمة** يبدأ الظهور بعد اكتمال التصنيف، أي لا يظهر في:

```text
new
pending_triage
```

ويظل ظاهرًا طوال المراحل النشطة للبلاغ.

بعد إغلاق البلاغ يبقى ظاهرًا فقط للأدوار الخمسة المذكورة في قسم التقرير الأرشيفي، ويختفي عن الفني وبقية الأدوار.

المسار المستخدم:

```text
GET /api/tickets/:id/pdf?document=task
```

وثيقة المهمة مختصرة ومخصصة للتنفيذ الميداني، بخلاف التقرير الأرشيفي الشامل.

## 5. تبويب بلاغات الإنشاءات في صندوق البلاغات

أضيف تبويب **بلاغات الإنشاءات** داخل:

```text
/tickets/inbox?tab=construction
```

ويستخدم نفس آلية التبويب الموجودة في صفحة البلاغات:

```text
/tickets?tab=construction
```

### نطاق العرض

- مدير الإنشاءات والمشتريات يُوجّه تلقائيًا إلى تبويب الإنشاءات.
- الأدوار الإدارية المخولة تستطيع التنقل بين البلاغات العامة والإنشائية.
- التبويب يعرض فقط البلاغات المصنفة على الجهة:

```text
maintenance_report_department_construction
```

مع بقاء نطاق الخادم حسب المسؤول الموجّه إليه البلاغ.

## 6. تثبيت الفني بعد إعادة الإسناد

بعد إسناد أو إعادة إسناد الفني:

- يظهر اسم الفني الحالي في حقل ثابت باسم **الفني المسند حاليًا**.
- لا تبقى قائمة الاختيار مفتوحة بصورة تسمح بالتغيير غير المقصود.
- يظهر زر مستقل باسم **تغيير إعادة إسناد الفني**.
- عند فتح التغيير يجب اختيار فني مختلف؛ يرفض الخادم اختيار الفني الحالي نفسه.
- يبقى سبب إعادة الإسناد مطلوبًا عند تغيير الفني.

### الأدوار المخولة بإدارة الإسناد

- `maintenance_manager`
- `construction_procurement_manager` ضمن البلاغ الإنشائي الموجه إليه.
- `general_maintenance_manager` ضمن بلاغات الصيانة العامة.
- `admin`
- `owner`

لا يملك الفني أو المشرف أو أدوار المشتريات الأخرى صلاحية تغيير الإسناد.

## 7. الحماية في الخادم

تم فصل نوعي وثيقة PDF والتحقق من الصلاحية في الخادم، وليس فقط إخفاء الأزرار:

- `document=archive`: يتطلب إغلاق البلاغ ودورًا مخولًا.
- `document=task`: يتطلب أن يكون البلاغ قد تجاوز مرحلة الفرز، ومع الإغلاق يقتصر على الأدوار المخولة.

كما يرفض إجراء إعادة الإسناد اختيار الفني المسند نفسه.

## 10. قائمة تحقق يدوية قبل الاعتماد

1. بلاغ `pending_triage`: يظهر تعديل البلاغ، ولا تظهر طباعة المهمة أو التقرير الأرشيفي.
2. بعد الفرز: يختفي تعديل البلاغ وتظهر طباعة المهمة.
3. بلاغ نشط لمستخدم فني: تظهر طباعة المهمة، ولا يظهر التقرير الأرشيفي.
4. بلاغ مغلق للفني: يختفي زر طباعة المهمة والتقرير الأرشيفي.
5. بلاغ مغلق لأحد الأدوار الخمسة: يظهر زر طباعة المهمة والتقرير الأرشيفي.
6. صندوق البلاغات: يظهر تبويب الإنشاءات ويعرض نطاقه الصحيح.
7. إعادة الإسناد: يبقى اسم الفني مثبتًا، ولا تظهر قائمة التغيير حتى الضغط على الزر المستقل.
8. محاولة اختيار الفني نفسه: يرفض النظام العملية.

## 11. منع طلب شراء جديد في المسار A

عند اعتماد مسار الصيانة:

```text
A — إصلاح مباشر
```

يختفي زر **طلب شراء جديد** من صفحة تفاصيل البلاغ، لأن هذا المسار مخصص لتنفيذ الإصلاح مباشرة ولا يتطلب دورة شراء.

### الحماية المطبقة

- الواجهة تستخدم قاعدة مشتركة تمنع ظهور الزر عندما تكون قيمة `maintenancePath` مساوية لـ `A`.
- الخادم يرفض كذلك إنشاء طلب شراء أو حفظ مسودة أو إرسال مسودة مرتبطة ببلاغ مساره `A`، حتى عند محاولة فتح رابط الإنشاء مباشرة أو استدعاء API يدويًا.
- بقي السلوك السابق للمسارين `B` و`C` دون تغيير.
