# دليل الحذف الآمن للبلاغات (Tickets) في قاعدة بيانات CMMS

**تاريخ التوثيق:** 2026-08-03
**قاعدة البيانات:** TiDB (متوافقة مع MySQL)
**المرجع:** عملية حذف 15 بلاغًا تجريبيًا (عناوين تحتوي "تجربة")

---

## 1. لماذا هذا التوثيق؟

حذف صف واحد من جدول `tickets` مباشرة عبر `DELETE FROM tickets WHERE id = ...` **غير كافٍ وخطر**، لأن هناك جداول أخرى كثيرة ترتبط بالبلاغ عبر `ticketId` أو حقول مشابهة. حذف البلاغ فقط دون هذه الجداول يترك بيانات "يتيمة" (orphaned) تُسبب أخطاء لاحقًا في التطبيق أو تقارير غير دقيقة.

هذا الدليل يوثّق **كل الجداول المرتبطة بالبلاغات**، وترتيب الحذف الصحيح، والمنهجية الآمنة (نسخ احتياطي أولًا) التي استخدمناها فعليًا.

---

## 2. خريطة الارتباطات (Dependency Map) لجدول `tickets`

### أ) جداول ترتبط مباشرة بالبلاغ عبر `ticketId`
| الجدول | نوع الربط | ملاحظات |
|---|---|---|
| `ticket_status_history` | `ticketId` | سجل تغييرات الحالة |
| `ticket_confirmations` | `ticketId` | تأكيدات المُبلّغ |
| `inspection_results` | `ticketId` | نتائج الفحص/المعاينة |
| `pm_jobs` | `ticketId` | أعمال الصيانة الوقائية |
| `inventory_transactions` (+ `_legacy_orphans`) | `ticketId` | حركات المخزون |
| `purchase_orders` (+ `_legacy_orphans`) | `ticketId` | **طلبات الشراء — الأخطر، لها ارتباطات فرعية خاصة بها (انظر بند ب)** |

### ب) جداول ترتبط بشكل عام (Polymorphic) عبر `entityType` + `entityId`
| الجدول | الشرط |
|---|---|
| `attachments` | `entityType = 'ticket' AND entityId = <ticketId>` |
| `audit_logs` | `entityType = 'ticket' AND entityId = <ticketId>` |

### ج) جداول ترتبط عبر حقل مختلف الاسم
| الجدول | الحقل |
|---|---|
| `notifications` | `relatedTicketId` |

### د) إذا كان البلاغ مرتبطًا بطلب شراء (`purchase_orders`)، فهذا الطلب نفسه له ارتباطات فرعية يجب فحصها أولًا:
| الجدول | نوع الربط |
|---|---|
| `purchase_order_items` | `purchaseOrderId` (له قيد `onDelete: restrict` — **تمنع القاعدة حذف الطلب ما لم تُحذف أصنافه أولًا**) |
| `po_pricing_batches` | `purchaseOrderId` |
| `procurement_comments` | `purchaseOrderId` |
| `ocr_jobs` | `purchaseOrderId` |
| `warehouse_receipts` (+ `_legacy_orphans`) | `purchaseOrderId` |
| `warehouse_returns` | `purchaseOrderId` |

### هـ) وإذا وُجد سند استلام (`warehouse_receipts`)، فله بدوره:
| الجدول | نوع الربط |
|---|---|
| `warehouse_receipt_items` | `receiptId` |
| `inventory_transactions` | `receiptId` (⚠️ **يجب فحصه دائمًا** — إن وُجدت صفوف هنا فقد تأثر رصيد المخزون الفعلي، ويحتاج تصحيحًا يدويًا لرصيد `inventory.quantity` قبل الحذف) |

> ⚠️ **تنبيه هام:** لاحظنا في حالتنا أن سند استلام كانت حالته "confirmed" لكن لم توجد له أي حركة في `inventory_transactions` (فجوة بيانات موجودة في النظام) — لا تفترض أن الحالة "confirmed" تعني تلقائيًا وجود حركة مخزون، **افحص دائمًا** بالاستعلام مباشرة.

## 3. الترتيب الصحيح للحذف (من الأعمق إلى الأصل)

```
1. ocr_jobs                    (WHERE purchaseOrderId IN (...))
2. warehouse_receipt_items     (WHERE receiptId = ...)
3. po_pricing_batches          (WHERE purchaseOrderId IN (...))
4. procurement_comments        (WHERE purchaseOrderId IN (...))
   ↓
5. warehouse_receipts          (WHERE id = ...)
6. purchase_order_items        (WHERE purchaseOrderId IN (...))
   ↓
7. purchase_orders             (WHERE id IN (...))
   ↓
8. ticket_status_history       (WHERE ticketId IN (...))
9. ticket_confirmations        (WHERE ticketId IN (...))
10. inspection_results         (WHERE ticketId IN (...))
11. attachments                (WHERE entityType='ticket' AND entityId IN (...))
12. notifications              (WHERE relatedTicketId IN (...))
13. audit_logs                 (اختياري — عادة يُحتفظ به كسجل تدقيق دائم)
   ↓
14. tickets                    (WHERE id IN (...))  ← آخر خطوة دائمًا
```

**القاعدة الذهبية:** ابدأ دائمًا من الجدول الأبعد عن `tickets` (الأصناف والتفاصيل الفرعية)، وانتهِ بحذف `tickets` نفسها في آخر خطوة.

## 4. منهجية النسخ الاحتياطي (مهم: TiDB لا يدعم `CREATE TABLE ... AS SELECT`)

استخدم دائمًا خطوتين منفصلتين لكل جدول قبل حذفه:

```sql
-- الخطوة 1: نسخ البنية (فارغة)
CREATE TABLE _backup_YYYYMMDD_<table_name> LIKE <table_name>;

-- الخطوة 2: نسخ البيانات المستهدفة فقط
INSERT INTO _backup_YYYYMMDD_<table_name>
SELECT * FROM <table_name> WHERE <شرط الحذف نفسه>;
```

> استبدل `YYYYMMDD` بتاريخ العملية، و`<table_name>` باسم الجدول، و`<شرط الحذف نفسه>` بنفس شرط `WHERE` الذي ستستخدمه في `DELETE` — **يجب أن يتطابق الشرطان تمامًا** حتى تكون النسخة الاحتياطية مطابقة لما سيُحذف بالضبط.

هذه الجداول الاحتياطية هي جداول عادية **داخل نفس قاعدة البيانات** (وليست في مكان خارجي منفصل)، يمكن الرجوع إليها بـ `SELECT` أو `INSERT INTO ... SELECT * FROM _backup_...` لاسترجاع البيانات لاحقًا عند الحاجة.

**بعد التأكد التام (أيامًا لاحقة) أن الحذف كان سليمًا:**
```sql
SHOW TABLES LIKE '_backup_YYYYMMDD_%';   -- لعرض كل النسخ الاحتياطية دفعة واحدة
DROP TABLE _backup_YYYYMMDD_<table_name>; -- لحذف كل واحدة نهائيًا عند الاطمئنان
```

## 5. قالب جاهز لاستخدامه في عملية حذف بلاغات مستقبلية

استبدل `(IDS...)` بأرقام (`id`) البلاغات المستهدفة، وكرر الفحص قبل كل حذف:

### أ) فحص أولي (لمعرفة حجم الارتباطات قبل أي قرار)
```sql
SELECT 'ticket_status_history' t, COUNT(*) c FROM ticket_status_history WHERE ticketId IN (IDS...)
UNION ALL SELECT 'ticket_confirmations', COUNT(*) FROM ticket_confirmations WHERE ticketId IN (IDS...)
UNION ALL SELECT 'inspection_results', COUNT(*) FROM inspection_results WHERE ticketId IN (IDS...)
UNION ALL SELECT 'pm_jobs', COUNT(*) FROM pm_jobs WHERE ticketId IN (IDS...)
UNION ALL SELECT 'inventory_transactions', COUNT(*) FROM inventory_transactions WHERE ticketId IN (IDS...)
UNION ALL SELECT 'purchase_orders', COUNT(*) FROM purchase_orders WHERE ticketId IN (IDS...)
UNION ALL SELECT 'attachments', COUNT(*) FROM attachments WHERE entityType='ticket' AND entityId IN (IDS...)
UNION ALL SELECT 'audit_logs', COUNT(*) FROM audit_logs WHERE entityType='ticket' AND entityId IN (IDS...)
UNION ALL SELECT 'notifications', COUNT(*) FROM notifications WHERE relatedTicketId IN (IDS...);
```

### ب) إن ظهر `purchase_orders > 0`، افحص كل طلب على حدة قبل المتابعة:
```sql
SELECT po.id, po.poNumber, po.ticketId, po.status,
       (SELECT COUNT(*) FROM purchase_order_items WHERE purchaseOrderId = po.id) AS items_count
FROM purchase_orders po
WHERE po.ticketId IN (IDS...);
```
ثم لكل `po.id` ظاهر، افحص `ocr_jobs`, `po_pricing_batches`, `procurement_comments`, `warehouse_receipts` بنفس الطريقة (`WHERE purchaseOrderId = <po.id>`).

### ج) إن ظهر `warehouse_receipts > 0`، تحقق دائمًا من أثر المخزون قبل الحذف:
```sql
SELECT * FROM inventory_transactions WHERE receiptId = <receipt_id>;
```
**إذا رجعت صفوف (وليس فارغة):** توقف ولا تكمل الحذف قبل مراجعة رصيد `inventory.quantity` للصنف المتأثر يدويًا، لأن حذف الحركة سيترك الرصيد غير صحيح دون تصحيح صريح.

### د) نفّذ النسخ الاحتياطي لكل جدول ظهر فيه عدد > 0 (بالمنهجية في البند 4)

### هـ) نفّذ الحذف بالترتيب الوارد في البند 3، من الأعمق حتى `tickets`

### و) تحقق نهائي
```sql
SELECT COUNT(*) FROM tickets WHERE id IN (IDS...); -- يجب أن يرجع 0
```

## 7. ملاحظة مفتوحة (لم تُعالج بعد)

أثناء الفحص وُجد صنف غير مرتبط بهذه العملية باسم **"سكوكت تجربة"** في جدول `inventory` (id=224، `receiptId=210138`، الكمية=0) — بقايا اختبار قديم منفصل تمامًا عن الـ15 بلاغًا المذكورة أعلاه. لم يُحذف ضمن هذه العملية. يمكن فحصه والتعامل معه في جلسة منفصلة إن رغبت.

كذلك، لوحظ أن بنية جدول `tickets` الفعلية في القاعدة (عبر `DESCRIBE`) تحتوي أعمدة (`inspectionWorkflowStatus`, `maintenanceResponsibleDepartment`, وغيرها) غير موجودة في ملف الكود `drizzle/schema.ts` — يستحق مراجعة منفصلة لمزامنة ملف الـ schema مع الواقع الفعلي للقاعدة.
