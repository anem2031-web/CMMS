## الإصلاحات الثمانية الحرجة في الكود

### الإصلاح #1 — ثغرة IDOR في `deleteItem` و`editItem`
**الملف:** `server/routers/purchase/purchase-orders.router.ts`
**المشكلة:** الإجراء يتحقق من حالة/صلاحية `purchaseOrderId` المُرسل، لكن لا يتحقق أن `id` (الصنف) ينتمي فعلًا
لنفس ذلك الطلب. يسمح بحذف/تعديل صنف من طلب "ب" مكتمل عبر تمرير رقم طلب "أ" آخر قابل للتعديل.
**قبل:**
```js
const po = await db.getPurchaseOrderById(input.purchaseOrderId);
const item = await db.getPOItemById(input.id);
// لا يوجد تحقق من العلاقة بينهما
await db.deletePOItem(input.id);
```
**بعد:**
```js
if (item.purchaseOrderId !== input.purchaseOrderId) {
  throw new TRPCError({ code: "BAD_REQUEST", message: "هذا الصنف لا ينتمي لطلب الشراء المحدد" });
}
```
**لماذا:** بدون هذا التحقق، أي مستخدم بصلاحية عادية يستطيع تفريغ أي طلب من أصنافه أو تعديل بيانات طلب آخر مكتمل.

### الإصلاح #2 — حماية "آخر صنف متبقٍ" في `deleteItem`
**الملف:** نفسه أعلاه
**المشكلة:** يمكن حذف آخر صنف في طلب طالما حالته ضمن الحالات القابلة للتعديل، فيتحوّل الطلب لـ"رأس بلا بنود".
**الحل:**
```js
const allItemsInPO = await db.getPOItems(input.purchaseOrderId);
if (allItemsInPO.length <= 1) {
  throw new TRPCError({ code: "BAD_REQUEST", message: "لا يمكن حذف آخر صنف متبقٍ..." });
}
```
**لماذا:** هذا بالضبط الشكل الذي وُجد عليه الطلبات التسعة الفارغة أصلًا.

### الإصلاح #3 — شرط ميت في حذف الطلب الكامل
**الملف:** نفسه أعلاه (إجراء `delete`)
**المشكلة:** شرط الحماية كان يقارن `po.status` بقيم غير موجودة إطلاقًا في enum النظام
(`funded`, `partially_purchased`, `completed`) — فالشرط لا يتحقق أبدًا، ويستطيع أي `owner`/`admin` حذف أي طلب
مهما كانت حالته.
**الحل:** استُبدلت بقائمة `nonDeletableStatuses` تطابق فعليًا enum الحالات الحقيقي في `drizzle/schema.ts`
(`pending_accounting`, `pending_management`, `approved`, `partial_purchase`, `purchased`, `received`, `closed`).
**لماذا:** أخطر من ثغرة IDOR نظريًا — لا يحتاج أي حيلة، الحماية غير مفعّلة إطلاقًا مهما فعل المستخدم.

### الإصلاح #4 — تعطيل مسار الاستلام القديم غير الآمن (v1)
**الملف:** `server/routers/inventory/receipts.router.ts`
**المشكلة:** الصفحة الأمامية (`WarehouseReceive.tsx`) كانت مُعطَّلة (مُوجَّهة لـ `NotFound`)، لكن الإجراء
`receiveFromPurchase` بقي مسجَّلًا وقابلًا للاستدعاء المباشر عبر API، بلا أي تحقق من ملكية الصنف وبلا معاملة

**لماذا:** تعطيل الصفحة الأمامية لا يُعطِّل الإجراء في الخادم. هذا فسّر جزءًا من حادثة انفصال روابط الاستلام.

### الإصلاح #5 — غياب المعاملة الذرية عند إنشاء الطلب
**الملفات:** `purchase-orders.router.ts` (مساري `create` و`saveDraft`)، `server/_core/db/purchase.ts`
**المشكلة:** إنشاء رأس الطلب وبنوده كانا استدعاءين منفصلين تحت autocommit. فشل إدراج البنود بعد نجاح إنشاء
الرأس يترك "رأسًا بلا أصناف" للأبد.
**الحل:**
- `createPurchaseOrder` و`createPOItems` أصبحتا تقبلان `tx` اختياريًا.
- `createPOItems` ترفض الآن مصفوفة فارغة (رمي خطأ) بدل التجاهل الصامت.
- كلا المسارين يُغلِّفان الإنشاء داخل `db.withTransaction(...)`.
**لماذا:** هذا يمنع تكرار نمط "رأس بلا بنود" من نقطة الإنشاء الأولى، بمعزل عن أي سبب لاحق آخر.

### الإصلاح #6 — الاستنتاج الخاطئ من قائمة فارغة (`every()`)
**الملفات:** `server/routers/inventory/inventory.router.ts`، `server/routers/inventory/receipts.v2.router.ts`
**المشكلة:** `[].every(predicate)` تُعيد `true` دائمًا في JavaScript (صدق فارغ). عند فحص "هل كل الأصناف
اكتملت؟" على طلب بصفر أصناف نشطة، كانت النتيجة `true`، فيتحوّل الطلب لحالة `received` رغم عدم وجود أي صنف.
**الحل:** إضافة `activeItems.length > 0 &&` قبل كل استدعاء `every()` كان يفتقده.
**لماذا:** هذا لا يُنتج المشكلة، لكنه كان يُخفي حدوثها بتحويل أي طلب فارغ (لأي سبب) لحالة "مُستلم" مضلِّلة.

### الإصلاح #7 — إضافة مفاتيح خارجية حقيقية (Foreign Keys)
**الملفات:** `drizzle/schema.ts` + `drizzle/migrations/critical_fix_07_*.sql`
**المشكلة:** لا يوجد أي قيد مرجعي في قاعدة البيانات نفسها بين:
- `purchase_order_items.purchaseOrderId → purchase_orders.id`
- `warehouse_receipt_items.purchaseOrderItemId → purchase_order_items.id`
- `inventory_transactions.purchaseOrderItemId → purchase_order_items.id`

**الحل:** بعد تنظيف شامل لكل البيانات المخالفة القديمة (راجع قسم "تنظيف البيانات" أدناه)، طُبِّقت المفاتيح
الثلاثة فعليًا على قاعدة الإنتاج بتاريخ 2026-07-19:
```sql
ALTER TABLE purchase_order_items
  ADD CONSTRAINT fk_poi_purchase_order
  FOREIGN KEY (purchaseOrderId) REFERENCES purchase_orders(id) ON DELETE RESTRICT;

ALTER TABLE warehouse_receipt_items
  ADD CONSTRAINT fk_wri_po_item
  FOREIGN KEY (purchaseOrderItemId) REFERENCES purchase_order_items(id) ON DELETE SET NULL;

ALTER TABLE inventory_transactions
  ADD CONSTRAINT fk_invtx_po_item
  FOREIGN KEY (purchaseOrderItemId) REFERENCES purchase_order_items(id) ON DELETE SET NULL;
```
**لماذا:** خط الدفاع الأخير الذي يجعل تكرار كل هذه الحوادث **مستحيلًا تقنيًا** على مستوى القاعدة نفسها، بمعزل
عن أي خطأ برمجي مستقبلي، سكربت صيانة، أو استيراد بيانات.
**⚠️ لا تُعطِّل هذه القيود ولا تُنشئ endpoint جديدًا يتجاوز `foreign_key_checks` دون خطة احتواء مماثلة.**

### 2026-07-19 — إزالة زر "تصدير PDF" العام (بلا دفعة) من صفحة تفاصيل طلب الشراء
**الملف:** `client/src/pages/purchase/PurchaseOrderDetail.tsx`
**المشكلة:** كان يوجد زرّان لتصدير PDF: زر عام أعلى الصفحة (`handleExportPdf`, بلا `batchId`) يُصدِّر كل أصناف
الطلب من كل دفعات التسعير مجتمعة، وزر آخر لكل دفعة تسعير على حدة (`handleExportBatchPdf`, بـ `batchId`)
المُسمَّى صراحة "تصدير PDF لهذه الدفعة (لطلب العهدة)". مستند العهدة المالية يجب أن يعكس دفعة واحدة مُرسَلة
فقط (تسعير جزئي أو كامل الطلب دفعة واحدة — كلاهما يُنتج `batchId` واحدًا عبر `submitPricedBatch`)، فالزر العام
كان يخالف هذا المبدأ من حيث الأساس، بصرف النظر عن حالة الطلب.
**الحل:** حُذف الزر العام بالكامل مع الدالة `handleExportPdf` والحالة `exportingPdf` غير المستخدمتين بعده. بقي
زر الدفعة (`handleExportBatchPdf`) هو المسار الوحيد لتصدير مستند العهدة، وهو محمي فعلًا (راجع البند السابق)
من عرض أصناف ملغاة أو غير مُسعَّرة أو قيد المراجعة — الأخيرة مستحيلة أصلًا ضمن أي دفعة لأن `requestItemRevision`
يرفض العملية إن كان للصنف `batchId` أو لم تكن حالته `pending`.
**لماذا:** الزر العام لا يخدم أي سيناريو عمل حقيقي (كل تسعير، جزئيًا أو كاملًا، يمر عبر آلية الدفعات نفسها)،
وإبقاؤه كان يسمح بتصدير مستند عهدة غير دقيق يجمع مبالغ من دفعات متعددة معًا.

### 2026-07-19 — تفعيل زر "تصدير PDF لهذه الدفعة" فور إرسال المندوب للدفعة (بدل انتظار اعتماد الحسابات)

(`pending_accounting`, `pending_management`, `approved`) بغض النظر عن حالة اعتماد الحسابات.
**لماذا:** هذا المستند مرتبط بالمندوب (منشئ طلب العهدة) لا بالحسابات (الجهة المعتمِدة)، فربط تفعيله باعتماد

### 2026-07-19 — إمكانية تعديل البلاغ طالما لم يُصنَّف بعد (يختفي بعد التصنيف)
**الملفات:** `server/routers/tickets/tickets.router.ts` (إجراء `update`)، `client/src/pages/tickets/TicketDetail.tsx`
**المطلوب:** بعد إنشاء بلاغ جديد وحفظه، يبقى قابلًا للتعديل طالما لم يُصنَّف بعد (لا يزال في حالة
`pending_triage`)؛ بمجرد تصنيفه (انتقاله لأي حالة تالية عبر إجراء الفرز `triage`)، يختفي خيار التعديل نهائيًا.
**الحل:**
- **الخادم:** إجراء `update` كان يسمح بالتعديل في أي حالة عدا `closed`. أصبح الآن مقيَّدًا بشرط صريح:
  ```js
  if (ticket.status !== "pending_triage") {
    throw new TRPCError({ code: "BAD_REQUEST", message: "لا يمكن تعديل البلاغ بعد تصنيفه" });
  }
  ```
  هذا الشرط يُطبَّق على الجميع (المُبلِّغ والأدوار المميّزة) بلا استثناء — العلاقة بصلاحية الدور (من يملك حق
  التعديل أصلًا) بقيت كما هي، والجديد هو ربط إمكانية التعديل بحالة التصنيف بدل الاكتفاء بحالة الإغلاق فقط.
- **الواجهة:** لم تكن توجد أي واجهة تعديل للبلاغ من الأساس. أُضيف:
  - زر تعديل (أيقونة قلم) بجانب عنوان تفاصيل البلاغ، يظهر فقط عند تحقق شرط `canEditTicket`
    (الحالة `pending_triage` + صلاحية الدور/الملكية — نفس منطق الخادم مطابقًا على الواجهة لتفادي وميض الزر
    ثم رفض الطلب).

### 2026-07-20 — إصلاح انقطاع الترجمة التلقائية للبلاغات (لا تصل أبدًا في بعض الحالات)
**الملفات:** `server/services/translation/translationEngine.ts`، `server/_core/index.ts`
**المشكلة المُبلَّغ عنها:** بلاغ أُنشئ بالإنجليزية، وبعد أكثر من 3 ساعات ومرور اللغة إلى العربية، ظل النص
الإنجليزي كما هو دون أي ترجمة.
**التشخيص:**
1. الترجمة تبدأ تلقائيًا في الخلفية فور إنشاء البلاغ عبر `queueTranslation` (لا يوجد زر يدوي مطلوب).
2. تحقق الاستعلام المباشر (`SELECT ... FROM translation_jobs WHERE ...`) أن **لا توجد أي مهمة ترجمة مسجَّلة
   إطلاقًا لهذا البلاغ** — ليست حتى `pending` أو `failed`، بل معدومة تمامًا. هذا يعني أن استدعاء
   `queueTranslation` نفسه فشل بصمت عند لحظة إنشاء البلاغ (مثال محتمل: انقطاع اتصال مؤقت بقاعدة البيانات)،
   وبما أنه مصمَّم كـ"أطلق ونسَ" (`fire and forget`، متعمَّد كي لا يُبطئ إنشاء البلاغ)، لم يترك أي أثر سوى
   سطر في سجلات الخادم (`console.error`) لا يراه أحد.
3. اكتُشف أيضًا أن الكود يحتوي بالفعل على دالة `recoverPendingTranslations` جاهزة تمامًا لاستعادة المهام
   العالقة (`pending`/`processing`)، لكنها كانت تُستدعى **مرة واحدة فقط عند إقلاع الخادم** (`setTimeout`
   لمرة واحدة لا `setInterval` دوري) — فأي مهمة تُفقَد بسبب إعادة تشغيل الخادم أثناء انتظار مؤقت إعادة
   محاولتها الداخلي (`setTimeout` آخر في نفس الملف عند فشل المهمة) تبقى عالقة للأبد حتى إعادة التشغيل التالية.
   لكن هذه الدالة وحدها **لا تغطي حالة البلاغ المُبلَّغ عنه**، لأنه لا توجد له مهمة من الأساس لتُستعاد.
**الحل:**
- دالة جديدة `queueMissingTranslations()`: تفحص البلاغات الحديثة (آخر 7 أيام) وتكتشف أيها **لا يملك أي سجل
  ترجمة إطلاقًا** (وليس فقط "فاشل" أو "معلَّق")، وتُعيد استدعاء `queueTranslation` لها من الصفر.
- تحويل استدعاء `recoverPendingTranslations` من مرة واحدة عند الإقلاع إلى **دوري كل 30 دقيقة**
  (`setInterval`)، مع استدعاء `queueMissingTranslations` معها في نفس الدورة.
**لماذا:** هاتان الفجوتان معًا (فشل صامت بلا أثر + استعادة تعمل مرة واحدة فقط) تعنيان أن أي عطل عابر عند لحظة
إنشاء أو ترجمة بلاغ قد يترك حقل الترجمة معطوبًا للأبد دون أي فرصة تلقائية للتصحيح. الإصلاح يضمن أن أي بلاغ
"سقط من النظام" يُكتشَف ويُعاد تلقائيًا خلال 30 دقيقة كحد أقصى، دون تدخل يدوي.
**ملاحظة تشغيلية:** هذا الإصلاح لا يُترجم البلاغات القديمة فورًا لحظة النشر؛ أول تشغيل دوري (خلال 30 دقيقة
من إعادة تشغيل الخادم بعد النشر) سيلتقطها تلقائيًا. للتعجيل بترجمة بلاغ محدد فورًا دون انتظار الدورة، يمكن
تعديل عنوانه أو وصفه تعديلًا طفيفًا (حرف واحد) وحفظه ثم التراجع عن التعديل وحفظه مجددًا — كل حفظ فيه تغيير
فعلي في النص يُعيد استدعاء `queueTranslation` عبر إجراء `update` الموجود أصلاً.

### 2026-07-21 — فلترة طلبات الشراء بحسب حالة صنف تابع لها (ملغى الشراء / بحاجة مراجعة)

### 2026-07-28 — ترتيب وفلترة طلبات الشراء بتاريخ الإرسال لا تاريخ إنشاء المسودة

**Commit:** `f6d808b` — `fix(purchase-orders): sort/filter by submission date, not draft creation date`

**المشكلة (أبلغ عنها صاحب المشروع):** المستخدم ينشئ مسودة طلب شراء وقد تبقى أسبوعين قبل إرسالها رسميًا.

**تأكيد السبب من الكود:** `db/purchase.ts:190` كان يرتّب بـ`desc(purchaseOrders.createdAt)`، وفلاتر التاريخ

- `list()` يرتّب **ويفلتر** بـ`COALESCE(submittedAt, createdAt)`.

**خاصية الأمان الجوهرية (COALESCE):** الطلبات الموجودة حاليًا `submittedAt = NULL`، فتحتفظ **بترتيبها
وسلوك فلترتها الحاليين تمامًا** — لا حاجة لتعبئة رجعية ولا تخمين تواريخ، ولا يتزحزح أي شيء بالبيانات
التاريخية.

**قرار مقصود — لم نُعدّل `createdAt`:** اقترح صاحب المشروع مبدئيًا استبداله بتاريخ الإرسال. رفضتُ ذلك لأن
مسحه **يُتلف معلومة لا تُسترجع** (كم بقيت المسودة قبل الإرسال — مؤشر إداري مفيد)، ويناقض `audit_logs` الذي

**بديل دُرس ورُفض:** تأجيل منح رقم طلب الشراء حتى الإرسال (لتفادي فجوات الترقيم من مسودات محذوفة). تحققنا أن
المسودات لا تُحذف إلا من `owner`/`admin` ولا يوجد زر حذف لمنشئها، فالفجوات نادرة جدًا — بينما التعديل يمتد
للواجهة والبحث والإشعارات. إصلاح الترتيب وحده يحل الشكوى بالكامل.

**أثر التعديل على سير العمل: صفر.** تحققنا أن لا مسار انتقال مرحلة، ولا فحص صلاحية، ولا اعتماد، ولا إشعار،
ولا سجل تدقيق يقرأ `createdAt` — الانتقالات مبنية على `status`، والأختام الزمنية تُسجَّل ولا يُبنى عليها شرط.

**❓ سؤال مفتوح لصاحب المشروع (لم يُغيَّر هنا):** دالة `resubmit` (من `revision_needed` إلى `pending_review`)
لا تُحدِّث `submittedAt`، فالطلب المُعاد بعد مراجعة يحتفظ بتاريخ إرساله الأول ولن يعود لأعلى القائمة. قد

### 2026-07-28 — عرض "تحتاجني الآن" كواجهة افتراضية لصفحة طلبات الشراء

**Commit:** `cb02bf6` — `feat(purchase-orders): add "needs my action" default view`

**الشكوى المعالَجة (بكلام صاحب المشروع):** «الطلبات كثيرة ولا أعرف ما يحتاج موافقتي فيضيع ضمن صفوف الطلبات،
ولا أعرف موقع الطلب الآن، ولا أعرف ما تم شراؤه بالكامل أو جزئيًا — والمستخدمون مشغولون ويريدون الفهم من
النظرة الأولى.»

**القرار التصميمي الجوهري:** "تحتاجني الآن" ليست «الطلبات بمرحلتي»، بل **ثلاث فئات مختلفة**:

| # | الفئة | لمن | كيف تُحدَّد |
|---|---|---|---|
| 1 | طلب بمرحلة يستطيع دور المستخدم التصرف فيها | حسب الدور | `canPerformAction()` من الحارس المركزي |
| 2 | طلب رُدّ لمنشئه (`revision_needed`) | منشئ الطلب | حالة الطلب + الملكية |
| 3 | صنف ملغى أو يحتاج مراجعة | منشئ الطلب | `canPerformItemAction()` من الحارس |

**الفئتان 2 و3 هما الأخطر عمليًا** — حالة الطلب العامة لا تدل إطلاقًا على أن الكرة بملعب المستخدم، بينما
الطلب **واقف تمامًا** حتى يتصرّف. الفئة 3 على مستوى **الصنف**: طلب فيه 5 أصناف وواحد ملغى يظهر مرة واحدة،
والتفصيل داخل نص السبب (`صنف ملغى يحتاج قرارك — 1 من 5 أصناف`).

**مبدأ ملتزَم به:** ملف `actionable.ts` **لا يعرّف أي صلاحية جديدة إطلاقًا** — يفوّض كل سؤال «هل يستطيع هذا
المستخدم التصرف؟» للحارس المركزي (`server/_core/authz`). فما يُعرض هو بالضبط ما يستطيع المستخدم تنفيذه
فعليًا. أُضيفت `getPOItemsForPOs()` لجلب الأصناف دفعة واحدة وتفادي استعلام لكل طلب (N+1).

**الواجهة:** جملة ملخص (`لديك 3 طلبات تحتاج تدخلك`)، تبويبان، وقائمة مختصرة (الرقم / السبب / ملخص الشراء
الجزئي / زر إجراء واحد). **لا تظهر الحالات التقنية إطلاقًا** — `pending_management` تصير «يحتاج اعتمادك
الإداري». الجدول الحالي بكل فلاتره وترقيم صفحاته والتصدير والحذف **لم يُمس**، ويبقى كاملًا تحت «جميع
الطلبات»: لم يُحذف شيء، أُضيف مدخل أذكى أمامه فقط.

**استُبعد عمدًا (باتفاق أثناء التصميم، تفاديًا للوعد بما لا تدعمه البيانات):**
- **«ما تغيّر منذ آخر زيارة»** — أُلغيت كليًا: المستخدمون يبقون بحساباتهم مفتوحة طوال اليوم فتموت الميزة بعد
  أول استخدام، وجملة الملخص تجيب عن السؤال الأهم أصلًا («ما المطلوب مني؟» لا «ما صار بالنظام؟»).
- **«منها طلبان متأخران»، تبويب الاستثناءات، الترتيب الذكي** — الأربعة تحتاج أختامًا زمنية لدخول كل مرحلة،
  وهي غير موجودة بعد.
- **الأوامر الصوتية والتحديث اللحظي** — حُذفا من الخطة نهائيًا (تكلفة عالية، استخدام نادر، واعتماد على خدمة
  ذكاء اصطناعي توقفت فعليًا بنفس اليوم بسبب الرصيد).

## 2026-08-05 (متابعة 2) — فلترة شاشة المستودع حسب المخزن، إخفاء الأصناف الصفرية، وتقييد تعديل اسم المخزن الفرعي

هذا البند يوثّق كل ما جرى **بعد** بند "متابعة" أعلاه (سلة التحويل المجمَّعة)، بنفس يوم 2026-08-05.

### 1) شاشة المستودع (`client/src/pages/inventory/Inventory.tsx`) — فلترة حسب المخزن + إجمالي الكميات

قبل هذا التعديل، شاشة المستودع كانت تعرض **كل** أصناف كل المخازن دفعة واحدة بلا أي تمييز بينها، رغم وجود
ميزة المخازن الفرعية فعليًا (البنود السابقة). التعديل:

- **حقل "المخزن"** كأول عنصر تفاعلي بالصفحة (قائمة منسدلة من `trpc.warehouse.list`). يُختار **المخزن

  يشاء.
- **كل الجدول والبحث والفرز وفلتر التاريخ أصبحت مقتصرة على المخزن المختار فقط.**
- **⚠️ قرار توافق مهم بخصوص الأصناف القديمة غير المرتبطة بأي مخزن:** أغلب أصناف المخزون الحالية أُنشئت قبل
  ميزة المخازن الفرعية ولذلك `inventory.warehouseId` فارغ (`NULL`) لها. لتفادي ظهور "المخزن الرئيسي" فارغًا
  رغم وجود بيانات فعلية:
  - **المخزن الرئيسي**: يعرض الأصناف المرتبطة به صراحة + **كل الأصناف القديمة بلا `warehouseId`** (تُعامَل
    كتابعة للرئيسي افتراضيًا).
  - **أي مخزن فرعي**: يعرض فقط الأصناف المنقولة إليه فعليًا (تطابق تام بلا أي استثناء).

  **هذا قرار عملي وليس مطلوبًا صراحة من صاحب المشروع** — إن أراد سلوكًا مختلفًا (مثلاً: عدم احتساب الأصناف
  غير المرتبطة ضمن أي مخزن حتى تُنقَل يدويًا) يحتاج تعديل صريح لاحقًا في `visibleWarehouseItems`/`warehouseItems`
  بنفس الملف.

- **بطاقة إحصائية جديدة "إجمالي الكميات بالمخزن المختار"** (لون أخضر، بجانب بطاقتَي عدد الأصناف والمخزون
  المنخفض الموجودتين مسبقًا) — قيمة **محسوبة تلقائيًا فقط** (مجموع `quantity` لكل الأصناف الظاهرة)، لا تقبل
  أي إدخال أو تعديل يدوي لأنها ليست حقل إدخال أصلًا.

### 2) خيار "إخفاء الأصناف ذات الرصيد صفر" — نفس الشاشة

- Checkbox يظهر **فقط بعد اختيار مخزن** (تحت حقل اختيار المخزن مباشرة).

  التأشير وقتما يشاء.
- **قرار صريح من صاحب المشروع**: هذا الخيار **يؤثر أيضًا على البطاقات الإحصائية الثلاث** (عدد الأصناف،

  أصناف المخزن — هذا قرار مقصود ومؤكَّد صراحة من صاحب المشروع في هذه الجلسة.**

### 3) تقييد تعديل مسمى المخزن الفرعي — أدمن ومالك فقط

**صلاحية جديدة `adminOwnerProcedure`** أُضيفت لـ`server/routers/_shared/procedures.ts`:

```ts
export const adminOwnerProcedure = roleMiddleware([]);
```

**ملاحظة تقنية مهمة لأي جلسة قادمة:** تمرير مصفوفة فارغة لـ`roleMiddleware` يعني عمليًا "أدمن ومالك فقط
تلقائيًا" — لأن فحص `roleMiddleware` الداخلي (أعلى نفس الملف) يسمح دائمًا للدورين `ADMIN`/`OWNER` بغض النظر
عن محتوى القائمة الممرَّرة. **لا تُضِف صراحة `APP_ROLE.ADMIN`/`APP_ROLE.OWNER` لهذه القائمة** — إضافتهما لا
تُغيّر السلوك لكنها تُربِك القارئ لاحقًا بخصوص هل القائمة الفارغة مقصودة أو خطأ سهو.

- إجراء `trpc.warehouse.update` (تعديل اسم/وصف/تفعيل مخزن) كان مقيَّدًا سابقًا بـ`warehouseProcedure`
  (يشمل دور `warehouse` العادي + أدمن/مالك) — **أصبح الآن مقيَّدًا حصريًا بـ`adminOwnerProcedure`**، بحيث لا

## 2026-08-08 (متابعة) — تطبيق ترحيل `ticket_items` يدويًا على قاعدة الإنتاج + ملاحظة توافق TiDB

### ما تم فعليًا

صاحب المشروع طبّق ترحيل `ticket_items` (الموثَّق بالبند أعلاه) **يدويًا خطوة بخطوة** على قاعدة الإنتاج

1. `CREATE TABLE ticket_items (...)` — نجح.

   ```sql
   CREATE TABLE tickets_backup_20260808 AS SELECT * FROM tickets;
   ```

   ```sql
   CREATE TABLE tickets_backup_20260808 LIKE tickets;
   INSERT INTO tickets_backup_20260808 SELECT * FROM tickets;
   ```

4. أمر الإدراج الرئيسي (نقل بيانات كل البلاغات القائمة إلى `ticket_items`) — **نجح**.

## 2026-08-08 — ثغرة صلاحيات مكتشَفة بالفرز المتعدد + إعادة تخطيط الخطوات المتبقية (قرار موثَّق، بلا كود بعد)

### الثغرة المكتشفة

أثناء اختبار صاحب المشروع للخطوة 2 (فرز بلاغ MT-2026-00212 على جهتين معًا)، تبيّن أن **الجهة الثانوية
تصلها إشعار بنص مهمتها لكنها تُمنع من فتح البلاغ نفسه** برسالة "ليس لديك صلاحية للاطلاع على هذا البلاغ".

**السبب الجذري المؤكَّد بالتتبّع:**

```ts
// server/routers/tickets/tickets.access.ts
export function isConstructionTicketAssignedToUser(user, ticket) {
  return user.role === CONSTRUCTION_PROCUREMENT_MANAGER &&
    ticket.maintenanceResponsibleDepartment === CONSTRUCTION &&   // ⚠️ عمود البلاغ الواحد فقط
    ticket.maintenanceResponsibleManagerId === user.id;
}
```

`routeTicketToMultipleDepartments` (الخطوة 2) تكتب على عمود `tickets.maintenanceResponsibleDepartment`
بيانات **الجهة الأولى فقط** (الجهة الرئيسية) — بقية الجهات تُسجَّل حصرًا في `ticket_items`. وبما أن قاعدة
الصلاحيات أعلاه، وكذلك فلاتر القوائم (`tickets.list`, `getTicketsInboxCounts`, والفلترة اليدوية بشاشة
الفرز `TriageDashboard.tsx`)، **كلها تقرأ عمود البلاغ الواحد ولا تعرف بوجود `ticket_items` إطلاقًا** —
أي جهة ليست الجهة الأولى تُمنع تمامًا من رؤية أو فتح بلاغاتها، رغم وصول الإشعار إليها.

**هذه ليست حالة حافة نادرة — ستتكرر مع كل فرز متعدد جهات دون استثناء.**

### القرار: رفض الحل المؤقت، اعتماد إصلاح معماري جذري

اقتُرح ابتداءً حل ضيق: توسعة الاستثناء القائم لمدير الإنشاءات (نفس نمط استثناء "قراءة فقط لطلب شراء
مرتبط" الموجود بـ`assertTicketReadable`) ليشمل أيضًا "أو له بند بـ`ticket_items`". **صاحب المشروع رفض هذا
صراحةً** ("لا اريد حل مؤقت اريد حل حقيقي وللمستقبل") لأن المشكلة موجودة بأربع طبقات مختلفة (الصلاحيات
+ 3 مواضع فلترة قوائم)، وترقيع موضع واحد يترك البقية معطوبة.

**القرار المعتمد:** `ticket_items` يصبح **مصدر الحقيقة الوحيد** للرؤية والقوائم، بدل عمود
`tickets.maintenanceResponsibleDepartment` وحده. السؤال يتغيّر من "ما جهة هذا البلاغ؟" (عمود واحد) إلى
"هل لهذا المستخدم بند ضمن بنود هذا البلاغ؟" — سؤال يعمل بلا فرق بين بلاغ ببند واحد (كل البلاغات القديمة)
أو عدة بنود (الجديدة)، ويُلغي الحاجة لاستثناءات متناثرة مستقبلًا.

### إعادة تخطيط الخطوات المتبقية — 5 خطوات مترابطة بدل الترقيم القديم 3→7

بعد نقاش، اتُّفق على توسعة الخطة القديمة (فحص+مسار / شراء+صيانة خارجية / تفاصيل البلاغ / إغلاق+تقارير /
توثيق) إلى **5 خطوات معاد صياغتها** تدمج إصلاح الصلاحيات كأساس أول، وعرض البنود كبطاقات كطلب صريح جديد:

1. **الأساس — إصلاح الصلاحيات جذريًا** (يحل الثغرة أعلاه نهائيًا): تعميم `isTicketVisible`/

   `ticket_items`، تحديث فلاتر `tickets.list`/`listPaginated`، وإزالة الفلترة اليدوية المكرِّرة

3. **التنفيذ:** نقل اختيار المسار A/B/C من مستوى البلاغ لمستوى البند — **مؤكَّد من صاحب المشروع بمثال

### السبب الجذري

`getNextTicketNumber()` (`server/_core/db/tickets.ts`) كانت تولّد الرقم بـ**البحث عن أعلى رقم موجود
حاليًا** (`SELECT ... ORDER BY ticketNumber DESC LIMIT 1` ثم `+1`). حذف بلاغ يحمل أعلى رقم يُرجع العدّاد
للخلف تلقائيًا، فيُعاد الرقم لبلاغ جديد مختلف تمامًا.

**البلاغات كانت الكيان الوحيد بالمشروع بهذا النمط** — كل العدّادات الأخرى (`delivery_number_counter`,
`disposal_number_counter`, `inventory_count_number_counter`, `inventory_settlement_number_counter`,
`warehouse_transfer_batch_number_counter`, `warehouse_transfer_number_counter`) تستخدم جدول عدّاد مستقل
منذ البداية. هذا يوافق "القاعدة #8" الموثَّقة بالتحليل الأول للمشروع.

### لماذا لم تختلط البيانات رغم تكرار الرقم

المفتاح الأساسي `tickets.id` (AUTO_INCREMENT) فريد دائمًا ولا يُعاد استخدامه أبدًا، وكل الروابط
(`external_maintenance_jobs.ticketId`, `purchase_orders.ticketId`, `ticket_items.ticketId`...) تشير إليه
لا لرقم العرض. **لا يوجد أي اختلاط فعلي بالبيانات** — الأثر محصور في اللبس البصري وبالتقارير والمستندات
المطبوعة التي تعرض رقم العرض.

### القرار: عدّاد مستقل، لا "حجز الأرقام المحذوفة"

اقترح صاحب المشروع ابتداءً "حجز رقم البلاغ المحذوف". اعتُمد بدلًا منه الحل الأبسط والمتوافق مع نمط
المشروع: **عدّاد يزيد للأمام دائمًا ولا يتأثر بالحذف** — يلغي الحاجة لتتبّع المحذوفات أصلًا، ويطبّق
مبدأ المشروع الموثَّق: "لا تُنشئ آلية جديدة إذا كانت هناك آلية موجودة يمكن توسيعها".
